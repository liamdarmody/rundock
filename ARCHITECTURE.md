# Rundock architecture

Rundock is a local Node.js server that exposes a vanilla-JS browser client over WebSocket and orchestrates runtime subprocesses (Claude Code by default; optionally the Codex CLI) to do the actual AI work. There is no cloud component, no server-side database, and no build step. The whole stack runs on your machine and reaches each provider only through its own CLI (Anthropic via Claude Code, OpenAI via Codex), which you authenticate yourself.

This document describes the process model, the workspace directory layout, and the codebase, in enough detail that a contributor can navigate the source after reading once. Implementation detail is left to the code; this document covers shape, boundaries, and where to look.

## The process model

Rundock has three classes of process at runtime.

```
+---------------------+        WebSocket         +---------------------+
|                     |  <-------------------->  |                     |
|   Browser client    |                          |   Node.js server    |
|   (public/app.js)   |   HTTP for assets and    |   (server.js)       |
|                     |   permission decisions   |                     |
+---------------------+                          +----------+----------+
                                                            |
                                                            | spawn / stream-json
                                                            v
                                              +-----------------------------+
                                              |    runtime subprocesses     |
                                              |   (one per active agent)    |
                                              +-----------------------------+
```

### The browser client

The browser is the visual interface. It renders the org chart, the conversation panel, the sidebar of past conversations, the file browser, the settings drawer, and the permission cards that pop up when an agent wants to run a tool. It holds no authoritative state. Reload it and the server still owns every conversation, every transcript, every running subprocess.

The client opens a single WebSocket to the server on load and uses HTTP for static assets and a small number of synchronous endpoints (workspace picker, permission decisions, agent listing). All ongoing conversation traffic flows over the WebSocket.

How `public/` is put together, and why it has no build step, is its own page: [CLIENT-ARCHITECTURE.md](docs/CLIENT-ARCHITECTURE.md). Read it before changing anything in `public/`.

### The Node.js server

`server.js` is the single server entry point. It does seven things, in roughly this order of importance.

1. **Discovers agents and skills** by reading the workspace directory (`.claude/agents/`, `.claude/skills/`, `System/Playbooks/`). See `discoverAgents` and `discoverSkills`.
2. **Spawns and manages Claude Code subprocesses.** Each active conversation has at most one running Claude Code child process at a time. The server tracks them in a `processes` map keyed by conversation ID.
3. **Bridges browser and Claude Code** by translating WebSocket messages from the client into stdin writes on the right subprocess, and by parsing the subprocess's stream-json stdout back into client-facing events.
4. **Intercepts delegation** so that when an orchestrator emits an Agent tool call, the server kills the orchestrator process, spawns the specialist with the right context, and streams the specialist's output to the client under the specialist's identity. See the next section.
5. **Persists conversation state** to `.rundock/` in the workspace (conversations index, transcripts, child PIDs, settings).
6. **Runs a lightweight scheduler** for routines defined in agent frontmatter. Every minute, it checks each agent's routines and invokes any whose schedule has come due.
7. **Mediates tool permissions.** Claude Code's PreToolUse hook calls back to the server over HTTP for any tool call that needs approval; the server forwards the request to the browser as a permission card and returns the user's decision to Claude Code.

**Who may drive it.** The server listens on loopback only (`HOST` in `server.js`). Every request then passes two checks before any route runs. `lib/local-origin.js` refuses a foreign `Host` (DNS rebinding) and a foreign `Origin` on a write or a WebSocket upgrade (other web pages). `lib/auth/index.js` then asks one question, `authenticate(req, port)`, of every WebSocket upgrade and every HTTP route except the page's static files, the two routes a browser uses to trade the printed link's code for a session token, and the permission hook's two routes: does this come from Rundock's own window? The desktop window carries the launch key in a header its main process adds (`electron/window-key.js`), and the desktop server accepts nothing else. A browser from source opens the printed link, whose one-time code (good once, for fifteen minutes; a link is printed only at start and when Enter is pressed in the terminal) the page trades for a session token kept in its own origin's storage and sent as a header and in the WebSocket handshake, never as a cookie; pictures and PDFs use a separate cookie that opens only those files. Tokens are kept as fingerprints, bound to their port and expiring. The launch key is made in memory at launch and never written to disk, the environment, a URL, the HTML or a log; the printed links hold only codes, which a terminal or a service journal may keep after they are dead. The hook's routes take a per-agent token instead, bound to that agent's conversation, so an agent can ask for a card in its own conversation and collect its own notice and nothing else. Two of the closed routes are privileged on the machine itself: the chat's reconnect card, when Claude Code's session has expired, asks the server to open a console running Claude Code's own login command, `claude auth login` (`POST /api/claude/reconnect`; only on Claude Code 2.1.41 or later, which first has it, so an older version or one whose version was never probed runs `claude` bare) and, when the person says they have finished, to run the one short turn that says whether it is connected again (`POST /api/claude/connection`). That turn runs from the home folder, never the temp folder, because `--print` skips the trust prompt and on Linux the temp folder is shared with every account; and only a failure whose words are a sign-in failure marks Claude Code signed out, while any other says the check could not tell. The desktop app opens the same console through its main process instead, answering only the main window's own top frame (`fromMainFrame`), and `lib/runtime/claude-console.js` holds the command per platform for both, behind one gate they share: one console opens at a time, and an ask in the few seconds after one opened is answered by that window rather than opening another. Only fixed words go on its command line besides the path to Claude Code, and a path the line cannot hold opens no console at all: one with a line break or NUL anywhere, or on Windows one with `&`, `^` or `%`, which the outer cmd would read. The answer is then that no console can open here, so the card shows the step to run by hand rather than a "Try again" that cannot work. On macOS, where Terminal runs the file it is opened on and takes no words after it, and AppleScript would raise an Automation prompt, the console is a two-line script of those fixed words, written first under the home folder in a folder only that account can use, removed and made again by exclusive create so it is never written through a link. Neither route answers an agent or the hook's token. Server-side writes into the workspace also refuse to leave it through a link (`lib/workspace/link-safe-write.js`). A remote client would use the same `authenticate` with a token issued by pairing, and must ship with transport security; the bind stays on loopback until then.

The server uses Node's native `http` module and the `ws` library for WebSocket. The runtime dependency surface is intentionally small: three production dependencies (`ws`, `marked`, and `electron-updater` for the packaged app's auto-update).

### The desktop app

The desktop app is the same server and the same client in an Electron shell. `electron/main.js` starts `server.js` inside the Electron process on a port the OS assigns, and opens one window on it with `electron/preload.js`, which gives the page the few things only the desktop can provide: the native folder picker, storage that lasts between launches, update notices and window chrome. Everything else behaves as it does in the browser.

**Advanced settings.** Environment variables the desktop app reads at launch. Most people never need them.

| Variable | What it does |
|---|---|
| `RUNDOCK_USER_DATA_DIR` | Runs the app on a profile of its own, kept in the folder given (an absolute path), instead of the usual one. That profile has its own single-instance lock, stored settings, setup record and update record, so a second copy can run beside the one already open, for example against a throwaway workspace. A relative path stops the app at launch rather than falling back to the usual profile. See `electron/user-data.js`. |

### Runtime subprocesses

Every conversation that is actively producing tokens has a runtime child process attached to it. For Claude Code agents (the default), Rundock spawns `claude` configured to read from the workspace directory, with the workspace's `.mcp.json` for MCP servers (merged with the per-user credentials in `.rundock/mcp-secrets.json` where there are any: see MCP credentials, below), with the workspace's `.claude/settings.local.json` for hooks, and with the agent's name passed so Claude Code loads the right system prompt from `.claude/agents/<slug>.md`.

Agents with `runtime: codex` run on the official Codex CLI instead, through ONE long-lived `codex app-server` process shared by the whole server (spawned lazily on the first Codex turn, supervised with restart-on-crash by `codex-appserver.js`). Each Codex conversation is a thread on that process and each message a streamed turn, with conversation continuity through thread resume and the agent's instructions carried in the first-turn prompt (Codex has no `--agent` equivalent). Codex agents use Codex's own sandbox (workspace-write, approvals on-request); sandbox escalations arrive as per-action approval requests that render as Rundock permission cards. The orchestrator always runs on Claude Code (delegation works through the Agent tool in Claude Code's stream, which Codex does not have). Environment detection and failure classification live in `codex.js`.

The subprocess speaks **stream-json** on stdout: a sequence of newline-delimited JSON events (assistant tokens, tool calls, tool results, system events). The server reads this stream line by line and forwards relevant events to the browser as WebSocket messages.

The subprocess's working directory is the workspace. Its file access, tool availability, and permissions are governed by Claude Code itself, not by Rundock. Rundock can only configure the spawn arguments and intercept the streamed output.

### Conversations: resume vs spawn fresh

Each Rundock conversation has its own Claude Code session ID. When a user opens a past conversation and sends a new message, the server spawns Claude Code with `--resume <sessionId>` so the model picks up the existing transcript from Claude Code's JSONL file. When a user starts a new conversation, the server spawns a fresh Claude Code subprocess and records the new session ID for next time.

Resume works because Claude Code persists every session as a JSONL transcript in the user's home directory (see The .rundock workspace directory, below). Rundock does not store conversation message content itself; it stores enough metadata to find and resume each session.

### Delegation: how the orchestrator hands off to a specialist

The delegation handoff works in five steps:

1. The orchestrator's Claude Code subprocess emits an Agent tool call event in its stream-json output, with the target specialist's slug as the argument.
2. The server detects the Agent tool call and treats it as a handoff signal. It kills the orchestrator's subprocess with `SIGKILL` so no further output reaches the client under the orchestrator's identity.
3. The server emits a `system: agent_switch` event to the client. The browser updates the conversation header and sidebar to show the specialist as the active agent.
4. The server spawns a new Claude Code subprocess with the specialist's slug. It passes a context block containing the conversation transcript so the specialist sees what happened before they were called.
5. The specialist's stream-json output flows back through the same bridge as the orchestrator's. The specialist signals completion with a `RUNDOCK:COMPLETE` or `RUNDOCK:RETURN` marker in its final response. On COMPLETE the work is done; on RETURN the server spawns the orchestrator again so it can pick up where it left off or hand off elsewhere.

This interception model is what makes "delegation that happens in front of you" visible. The agent name in the conversation header changes mid-stream, the sidebar updates, and the user sees specialists arrive without lifting a finger.

## The .rundock workspace directory

When Rundock first opens a workspace, it creates a `.rundock/` directory at the workspace root. This holds Rundock's own session state. It is added to `.gitignore` automatically on creation.

Contents:

| File or directory | Purpose |
|---|---|
| `state.json` | Workspace-level settings: setup completion flag, workspace mode (`notes` or `code`; a `knowledge` written by an earlier release reads as Notes, through `lib/workspace/mode.js`), whether agents are kept inside the workspace (`sandboxSwitch`), version. |
| `conversations.json` | Index of every Rundock conversation: ID, title, owning agent, last Claude Code session ID, timestamps. |
| `transcripts/<convoId>.json` | Lightweight conversation transcript for fast UI replay (role, agent, text). Capped to keep file size reasonable. |
| `child-pids.json` | Running Claude Code subprocess PIDs, used to clean up zombie processes on server restart. Each record carries the command it was spawned as, so a pid the OS has since recycled onto an unrelated process is not signalled. Not every platform can read a command line, and where none can be read the record is assumed to be ours rather than discarded: `pidRecordAlive` in `lib/runtime/claude.js` documents which sources exist, what each costs, and what that assumption gives up. |
| `search-index.db` | SQLite FTS5 index behind universal search (plus its `-wal`/`-shm` journal files). A **derived artifact**: delete it and the next workspace open rebuilds it from the files and transcripts it indexes. Never a source of truth. See Universal search, below. |
| `mcp-secrets.json` | Optional, and written by you rather than by Rundock. Per-user MCP credentials keyed by server name: the values that must not travel with the shared `.mcp.json`. See MCP credentials, below. Its `env` sets what each server starts with, so an agent's change to it always asks. |
| `mcp-runtime.json` | The shared `.mcp.json` with those values merged back in, written owner-only and pointed at by `--mcp-config`. A **derived artifact**, like the search index: regenerated before every spawn, safe to delete, and absent entirely unless `mcp-secrets.json` supplies a value. |
| `permission-hook.sh` | The launcher the runtime starts the permission hook through (`permission-hook.cmd` on Windows), rewritten on every open and named in `.claude/settings.local.json`. Whatever it says answers every permission check, so an agent's change to it always asks: see the files that decide what runs, under "An agent stays inside your workspace", below. |

What does **not** live in `.rundock/`:

- **Full message content.** The complete model output, tool calls, and tool results live in Claude Code's own JSONL transcripts at `~/.claude/projects/<projectHash>/<sessionId>.jsonl`. Rundock keeps a slimmer copy in `transcripts/` for UI replay, but the source of truth for the actual conversation is Claude Code's JSONL.
- **Theme and UI preferences.** These live in browser local storage. They do not sync between machines.
- **Agent and skill files.** These live in the workspace under `.claude/agents/` and `.claude/skills/`. Rundock reads them; it does not store them in `.rundock/`.

This split matters because it means Rundock's persistence layer is small and easy to reason about. The expensive thing (every token of every conversation) is owned by Claude Code, which Rundock does not need to replicate or back up.

### MCP credentials

`.mcp.json` is shared and `.rundock/` is not, and that difference is the whole of this. MCP servers commonly take an API key as a literal value, and `.mcp.json` sits at the workspace root with nothing excluding it, so on a workspace shared by repository the key reaches every clone and stays in the history from the first commit, where deleting the file afterwards does not remove it. The values can instead go in `.rundock/mcp-secrets.json`, keyed by server name:

```json
{ "notion": { "env": { "NOTION_API_KEY": "ntn_..." } } }
```

`lib/workspace/mcp-secrets.js` merges the two before every spawn and `getBareArgs()` points `--mcp-config` at the result. Its header comment carries the reasoning; four properties are worth knowing here.

- **Only `env` and `headers` are taken from the per-user file.** It supplies values and can never change which servers exist or the command named for one, so `.mcp.json` stays the single answer to what the workspace has. An `env` value can still change what that command does (`NODE_OPTIONS`, say), which is why an agent's change to the file always asks.
- **A literal credential left in `.mcp.json` still works.** Where no per-user value applies, the shared path itself is what gets passed, so a workspace that has not moved anything spawns exactly as it did. Moving a key is opt-in, and nothing scaffolds the per-user file or prompts for it.
- **The merged file wins over the copy Claude Code finds by itself.** Claude Code also discovers `.mcp.json` from the working directory, so a server named in both has two definitions. Measured against claude 2.1.245 with project-scope servers explicitly enabled: the `--mcp-config` entry is the one that starts, and only one server process starts.
- **It is replaced by rename, never rewritten in place.** The path is resolved again on every spawn, so a truncate-then-write would let an agent starting at that moment read a half-written config and come up with no MCP servers at all.

The environment was the alternative and was rejected. Claude Code expands `${VAR}` inside `.mcp.json`, so injecting the values into the spawn environment would need no file at all, but the environment of a spawned process is inherited by every child it starts: every other MCP server, and every shell command an agent runs. That would show one server's credential to all of them. An inline `--mcp-config` JSON string was rejected for the same kind of reason: it puts every credential in a command line, which on Linux any local user can read.

## File system layout per workspace

A workspace is any directory that contains, or is intended to contain, Claude Code agents. Rundock looks for these specific things:

| Path | Required | Purpose |
|---|---|---|
| `CLAUDE.md` | Recommended | Workspace-level rules and context. Loaded by Claude Code with every spawn. Used to derive the default agent identity if no agent files exist. |
| `.claude/agents/*.md` | Yes for a Rundock-ready workspace | Agent files. One file per agent. See AGENTS.md for the frontmatter reference. |
| `.claude/skills/<slug>/SKILL.md` | Optional | Skills the agents can use. Rundock matches them to agents either by explicit `skills:` frontmatter or by body-text mention of the slug. |
| `System/Playbooks/<slug>/PLAYBOOK.md` | Optional | Alternative skill location, scanned alongside `.claude/skills/`. Used by workspaces that pre-date the standard skill location. |
| `.claude/settings.local.json` | Optional | Hooks and per-workspace Claude Code settings. Forwarded to spawned subprocesses. |
| `.claude/settings.json` | Optional | The project's Claude Code settings, loaded for every agent spawned here. The hooks it names, and the scripts under `.claude/hooks/` they commonly run, are started by the runtime itself, so an agent's change to any of them always asks. |
| `.mcp.json` | Optional | MCP server configuration. Forwarded to spawned subprocesses. Shared with anyone the workspace folder is shared with, git included, so credentials belong in `.rundock/mcp-secrets.json` instead: see MCP credentials, above. Its stdio servers start as their own processes, so an agent's change to it always asks. |
| `.rundock/` | Created on first run | Rundock's own session state. See above. Auto-added to `.gitignore`. |

A workspace can also contain any other user files at the root or in subfolders. Rundock does not require a particular folder layout outside of the paths above. The browser's file panel reads from the workspace root and respects `.gitignore`.

How `public/` is organised, and the rules that keep it that way, is documented in [docs/CLIENT-ARCHITECTURE.md](docs/CLIENT-ARCHITECTURE.md).

**Production dependencies:** `ws` for WebSocket, `marked` for markdown rendering in conversation messages, `electron-updater` for the packaged app. Nothing else.

**Build artefacts:** none. `npm start` runs `node server.js` directly. There is no transpilation, no bundling, no minification step. If you change a file in `public/`, reload the browser. If you change `server.js`, restart the server.

**Where things are:**

- Agent discovery: `discoverAgents` in `lib/agents/discovery.js`. Reads `.claude/agents/*.md`, parses frontmatter, classifies each agent as `onTeam` (has `order`), `available` (has `type` but no order), or `raw` (neither, a bare Claude Code agent).
- Frontmatter parsing: `parseAgentFrontmatter`, `parseCapabilities`, `parseRoutines`, `parsePrompts`, `parseSkills` in `lib/agents/discovery.js`. Hand-rolled YAML subset, intentionally lenient.
- Skill discovery: `discoverSkills` in `server.js`. Scans both `.claude/skills/` and `System/Playbooks/`. Matches skills to agents via the explicit `skills:` array first, then falls back to body-text scanning for the slug.
- Subprocess spawn: `lib/runtime/claude.js`, which owns `getBareArgs()` for workspace context flags and `getSpawnEnv()` for environment variables (workspace mode, conversation ID). Codex spawns go through `lib/runtime/codex-glue.js`.
- Delegation interception: `lib/delegation/engine.js`. The interception happens inside the stream-json line handler; `lib/delegation/markers.js` holds the marker grammar and `lib/delegation/state.js` the scope-return bookkeeping.
- Markdown editor in the client: `public/views/files.js`, which owns the Tiptap lifecycle. Used for inline editing of agent files, skill files, and other markdown.
- Search engine: `search.js` (the whole file; its header comment records the design decisions). Server wiring: `ensureSearchEngine`, `reconcileSearchBeforeQuery`, `runUniversalSearch` in `server.js`. Client palette: `public/views/palette.js`.

## Delegation interception, briefly

Mechanically, the orchestrator-to-specialist handoff is a kill-and-respawn:

1. Orchestrator subprocess emits an Agent tool call.
2. Server detects it, kills the orchestrator process with `SIGKILL`, persists the orchestrator's last response to the transcript before the kill takes effect.
3. Server emits an `agent_switch` event over the WebSocket. The client redraws under the specialist.
4. Server spawns the specialist subprocess with the conversation history attached as the initial context.
5. Specialist runs to completion, emits `RUNDOCK:COMPLETE` or `RUNDOCK:RETURN`. On RETURN, the server spawns the orchestrator again so the conversation can continue.

The key design choice is that delegation looks like a real handoff to the user, not like a function call. The specialist runs in its own subprocess with its own system prompt and its own slice of context. The orchestrator does not stay alive while the specialist is working.

## Universal search, briefly

Universal search (the Cmd+K palette) queries four corpora: workspace files, conversations, agents, and skills. Files and conversations are indexed in SQLite FTS5 (`search.js`, using Node's built-in `node:sqlite`: no native dependency); agents and skills are tiny corpora filtered in memory at query time, so they can never go stale.

The things worth knowing that no single file states:

- **The index is a derived artifact.** `.rundock/search-index.db` rebuilds from workspace files and Claude Code's JSONL transcripts. There are no schema migrations: a `SCHEMA_VERSION` bump or a corrupt file deletes the database and rebuilds. Deleting it by hand is always safe.
- **Four reconcile triggers** keep it fresh: workspace open (`ensureSearchEngine`, synchronous full pass), every search (`reconcileSearchBeforeQuery`: conversations always, files behind a 2-second TTL), the `save_file` handler (immediate single-file index), and the end of every agent turn (`appendTranscript` → `noteSearchConversationActivity`).
- **Claude Code's JSONL stays the source of truth for conversations.** The indexer reads deltas past a per-session byte offset (append-only files make this safe); each session's delta lands in one transaction so a crash can never leave duplicate rows.
- **Session ownership is mark-authoritative.** A session's `session_marks` row decides which conversation owns it; `conversations.json` order is not trusted (new entries are unshifted to the head, so order-derived ownership would flip).
- **The grep fallback.** On runtimes without `node:sqlite` (Node 20/21), a capability probe routes every query to a bounded grep path instead. Search degrades; it never hard-fails. `RUNDOCK_SEARCH_DISABLE_SQLITE=1` forces this path for testing.
- **Trust boundary:** user queries never reach FTS5 as syntax (the sanitiser emits only quoted terms), and snippets carry control-character highlight markers that the client swaps for `<mark>` only after HTML-escaping.

The engine is exercised by `test/unit/search-*.test.js` (including a 10k-message performance suite) and `test/integration/search*.test.js`.

## Auditing the trust claims

The licence invites you to fork Rundock and audit it. If you take that up, the claims on the trust page reduce to a small set of named places; this is the ten-minute guided path.

- **"Every risky action asks the human first."** The permission decision path spans three layers, and all three are inspectable: the PreToolUse hook script (`scripts/`: what Claude Code consults before any tool runs), the server bridge (`server.js`: `/api/permission-request` for hook-originated requests, `requestServerPermission` for server-originated ones, both with a hard timeout that fails closed), and the client decision module **`public/permissions.js`**: the risk classification, the low-risk read-only auto-approve policy, and the rule that high-risk requests never offer a standing "Always allow" all live there, unit-tested and findable by name. **Connector (MCP) actions** are graded by the words of their action name (split on `_`, `-` and camelCase): in Notes mode the hook runs a read with no card (`MCP_READ_VERBS` in `scripts/permission-hook.js`), and a delete, send, reply or forward is never a read and is graded high risk, so it asks every time with no Always allow (a send, reply or forward shows "Allow once" and Deny, the look of every card that always asks), and when Rundock cannot be asked it is refused rather than allowed. An email draft, send, reply or forward, and a calendar event being created or changed, shows its fields on the card: recipients with the whole Bcc list always shown, subject and message, or an event's title, times and attendees with how many people an invitation is emailed to. They are read by generic field names in their common shapes, never by a named service (`public/connector-fields.js`); a send, reply or forward needs only a body to be read, since a reply can name nothing but its thread, and where it goes when it names a place rather than a person (a channel, chat, conversation, thread, user, recipient id or id; on a forward, an id or a thread names the message forwarded and is listed instead) is drawn as a row under its own key, cut at an address's length with the whole of it one click away, so a message that is not an email shows no empty Subject or To row, and a send is said to probably fail only when it reaches no one, names nowhere and carries no other field; drawn as text only (`connectorFieldsElement` in `public/views/chat.js`), each name and address in a bidirectional isolate of its own, with the raw tool name kept as a line at the foot; a request that matches neither keeps the plain card. Because the field card takes the place of the raw request, it leaves nothing out: a field found under more than one name (`to` and `recipients`, `body` and `htmlBody`, a top-level `to` beside `message.to`) is a row per name under the key it came under, up to ten rows with any more listed under Other fields, an entry in a shape the card cannot read is shown as written, and every key read as none of the fields is listed under Other fields: the first 25 shown and every other one, however many, in a disclosure beneath them, each value cut short on its own but none ever reduced to a count, and whenever anything is past the alias rows or the fields shown, the card says fields are folded away and must be checked before allowing. While a key is listed there that could hold who a request reaches (on a send, reply or forward any key; on an event or a draft anything but the ids, calendar, time zone, description and location almost every one carries, `WELL_KNOWN`), the recipient and attendee rows say to look there rather than that they are empty, and the card never says nobody is reached; a subject, title or message reads as usual. An email address anywhere in a field the card does not read, looked for through the whole value rather than the part shown, keeps the To row and adds a sentence to check Other fields, whatever a destination row says. A value the reader cannot handle (an epoch no date can hold, a date or time that does not exist, a value nested past eight levels) is shown as written, and if reading or drawing the fields throws anyway, the plain card is drawn instead, so no request goes without its card and no card stops the ones queued after it. A subject, title or message is clamped to a few lines with its whole text one click away, and once a card is on the page, again when the approvals dock shows itself, and whenever the host a card is in changes size (the chat being shown after the person was elsewhere, or the window made narrower, watched by `watchCardHost`), any value the browser has cut short gets that box too, however short the thresholds judged it (`revealClampedText`). A saved "Always allow" for a send or a delete is dropped by the store of saved answers (`readToolAllows` in `lib/workspace/boundary.js`) and refused if offered again. Code mode runs connector actions without a card. The flow is driven end to end through the real hook, server and card in `test/integration/connector-approvals.test.js`.

  **The guarantee is the operating-system row, and only that row.** `sandboxSettings` in `lib/workspace/scaffold.js` writes the runtime's command sandbox into the settings file the runtime is started with; it decides at syscall time and reads nothing, so no spelling defeats it. It configures write lists only (`filesystem.allowWrite`, and a `denyWrite` list carved out of it for the workspace's permission answer files, the runtimes' credential files, `~/.claude.json` with its backup, and what the runtime acts on outside the sandbox in a later session, including: `~/.claude/settings.json`, the `plugins`, `hooks`, `skills`, `agents`, `commands` and `backups` folders under `~/.claude`, `~/.claude-staging-oauth.json`, `~/.claude-local-oauth.json` and `~/.claude-custom-oauth.json`, which the runtime reads in place of `~/.claude.json` under a non-default sign-in, the workspace's own `.claude/settings.json`, and last of all the workspace's `.mcp.json`, whose servers the runtime starts as their own processes, `.rundock/permission-hook.sh`, the launcher the runtime starts the permission hook through, `.rundock/mcp-secrets.json`, which sets the environment those servers start with, and `~/.rundock-console`, the folder holding the script Rundock opens in Terminal to reconnect Claude Code), so it **governs writes and not reads**: measured under the shipped block, a command could still read `~/.ssh`, `~/.gitconfig`, `~/.zshrc` and `/etc/hosts`. The block once relied on the write allowlist being additive to the runtime's own defaults; in the field that assumption did not hold across installed runtime versions, and users met approval storms for the runtime's own bookkeeping. The allowlist now names, beyond the workspace and the npm cache, the runtime's bookkeeping explicitly rather than trusting defaults, from measurement against Claude Code 2.1.259 on 2026-09-03: fourteen subsystems under `~/.claude` written within a day of ordinary use (sessions, projects, shell snapshots, telemetry, tasks and caches among them), the `~/.claude.json` configuration written continuously (by the runtime's own process; the `denyWrite` list refuses it to sandboxed commands), the per-user temp directory under both of its macOS spellings (`/var/folders/...` and its `/private` real path), and `/tmp/claude` (with its `/private/tmp/claude` real path) for task output. Everything else in the home directory remains refused. The Claude Code 2.1.259 bundle carries that last group of `denyWrite` entries in its own built-in write-deny list (a static read of the bundle, not a live measurement), but Rundock pins no runtime version, so the block names them as well and the protection does not rest on which release is installed. The launcher is the exception: it is Rundock's own file, and only Rundock's block names it. When the workspace is the home folder, `~/.claude/agents` and `~/.claude/skills` are the workspace's own, and the block denies them all the same; Rundock writes them through its server, which no sandbox confines. A workspace opened inside one of those folders, `~/.claude/skills/<name>` for instance, has its shell writes refused there, as the runtime's own list refuses them too. It holds only while the installed `claude` supports the setting (Rundock pins no version, it spawns whatever `resolveClaudeBin` finds on PATH), and while the workspace's `settings.local.json` carries either no sandbox block or one Rundock wrote. Rundock keeps its own block current when a workspace is moved, renamed or copied, including to another machine or account: `isRundockSandbox` derives BOTH the workspace root and the home directory from the block itself rather than from this machine, and withdraws the block on a platform it would not have written one for. A block a person edited is never touched, so after a move it keeps a stale root and refuses writes inside the workspace, which is the safe direction and not a free one. A deny list trimmed to exactly the length an earlier build wrote reads as that build's block and is upgraded: only the lengths a build wrote are recognised, so a list cut short anywhere else stays as the person left it. Blocks written by the release that carried only two roots are still recognised as Rundock's own and upgraded on the next open. The temp-directory roots are this machine's, so a workspace opened on another machine reconciles them the same way the workspace root already travels. **The sandbox is its own switch, "Keep agents inside this workspace" (Settings, Permissions), and mode does not move it.** The switch is stored in `.rundock/state.json` as `sandboxSwitch`, `on` or `off`; on writes `enabled: true`, off writes `enabled: false`, and every writer of the block (the open-path reconcile, the switch's own `set_workspace_sandbox`, and the two working-folder writers) reads it through `sandboxShapeFor` in `lib/workspace/scaffold.js`. Absent, the switch is what the mode implied before it existed (off for Code, on otherwise), so a workspace from an earlier release reconciles to exactly the block it has and nothing is rewritten on open; the key is written only when the person acts, or when Rundock meets a workspace for the first time, which starts with the switch on in either mode. Off is there because a command sandbox can refuse process-launch primitives, such as a headless browser's startup check-in, categorically, no matter what folder permissions say, and no writable-roots entry can reach that; with it off the approval card remains the whole boundary, as on Windows and Linux. **Off states `false` rather than staying silent**, and the difference is the whole behaviour: `sandbox.enabled` is an OR across every settings layer: the shipped runtime reads `[...layers, localSettings].some(e => e?.sandbox?.enabled === !0)` (measured against Claude Code 2.1.266, read again in 2.1.281), although Claude Code's settings documentation (code.claude.com/docs/en/settings, "Settings precedence") describes a key taking the highest layer's value. So a block that merely omits the key leaves the sandbox on for anyone whose own `~/.claude/settings.json` enables it, and a block that says `false` cannot turn off a sandbox another layer turns on. Two earlier shapes tried the quieter versions, withdrawing the block entirely and then keeping it without an enable, and both left the off state inheriting a sandbox this paragraph says it does not have. The off block keeps the `filesystem` list beside the `false` so the folders a user named survive the round trip back on rather than being rebuilt from nothing. What the Permissions row reports is read from disk by `lib/workspace/sandbox-status.js`, never from the stored switch, by the same OR: where managed settings, the project's `.claude/settings.json` or the user's `~/.claude/settings.json` turn the sandbox on, the row shows On, read-only, names the file, and says Rundock's switch cannot turn it off while that file turns it on. A block a person wrote is replaced only through "Bring your custom rules into Rundock", after a review that lists the folders it turns into working folders and every rule it drops. Both earlier shapes are recognised as Rundock's own and upgraded on the next open, for the same reason the two-root block is: a block Rundock wrote but cannot recognise is one it can never rewrite or withdraw. Symlinked roots need no handling: measured, an allowlist root given through a symlink permits writes to the real path. macOS only by choice: native Windows has no sandbox, and Linux has one Rundock has not measured.

  **The card is a best-effort check over common spellings, and cannot be otherwise.** `scripts/permission-hook.js` canonicalises both sides of every comparison first (real paths through the filesystem, an unborn target through its nearest existing ancestor), so an inside path spelled through a symlink, a `/private` alias, or a case variant on the default case-insensitive filesystem is inside however it is written, which retired a class of false cards on symlink-synced workspaces. It classifies file tools by their path field, and shell commands (`Bash`, `PowerShell`) by two signals: the runtime's `dangerouslyDisableSandbox` retry flag, which is the operating system reporting a crossing it already refused, and paths recognised in the command text. The second reads a shell command without running it, and shell is a programming language: a target can be assembled, substituted, or spelled in a form nothing anticipated. Recognised today are absolute POSIX paths, drive letters, UNC names, `..` traversal on either separator, `~`/`$HOME`/`$env:USERPROFILE`/`%USERPROFILE%`, and any of those written after an `=` in a flag value or assignment, whether bare or quoted. On macOS and Linux a backslash in a Bash word is read as bash reads it, an escape when the word is unquoted and an ordinary character inside quotes, never a folder separator; a drive letter or UNC name, a Windows host, a Windows-shaped workspace and the `PowerShell` tool keep the Windows reading. **Code handed to an interpreter is read as code:** a here-document fed to `python`, `node`, `ruby` or `perl`, or written to a file with `cat >` or `tee`, and the program in a `-c` or `-e` argument, are judged by their quoted string literals, so `open('/etc/hosts')` and `'~/.aws/credentials'` are recognised while a division (`int(ms)/1000`), a lone `/`, a URL or an escape string such as `"\n\n"` is text. On macOS and Linux an absolute literal is a place only when its first folder exists on this machine, so a route, a URL path or a pattern such as `'/health'`, `'/docs/intro'` or `'/+'` is text while `/etc/…`, `/tmp/…`, `/var/…` and a home folder are not. Everything else in a here-document is read word by word as commands: a body fed to a shell or to any other command, data for a script (`python3 tool.py <<EOF`), a shell script written to a file, backticks and Perl's and Ruby's command quotes inside the code, and the substitutions an unquoted delimiter's body runs as it expands. A string handed to a shell with `-c` (`sh`, `bash`, `zsh`, `dash`, `ksh` or `fish`, named by a path or after `env`, `exec`, `command`, `nohup`, `nice`, `time`, `sudo`, `doas`, `timeout` or `xargs`, past their options and `timeout`'s duration) is read as commands, as a here-document fed to a shell is, and so is what it runs in turn: a shell's `-c` inside it, and its here-documents and code, a few levels deep. Relative paths are measured from where the command runs: the working directory the runtime reports, moved by a single literal `cd` that opens the command, or by one partway through an `&&` chain for the words joined to it, into a folder whose real path, through any link, is inside the workspace or a working folder. A folder the command has not made yet is judged by its deepest existing folder, resolved the same way, with the rest appended, and moves only the words its `&&` chain runs, since a `cd` into a missing folder fails and stops that chain; a `..` anywhere in a missing target moves nothing. Any less certain `cd`, or a `pushd` or `popd` anywhere in the command, leaves the starting folder as the base (a folder change is counted where the shell runs it as a command, so `cd` handed to `grep` as a pattern is not one), and a `cd` into a link that leads outside is reported as a crossing. For the files that decide what runs and Rundock's own answer files, a written word whose base is that starting folder is also tried from where each literal `cd` or `pushd` before it would land, each landing chained on the ones before it, so `if true; then cd .claude/hooks && echo x > pre.sh; fi` and `cd .claude && cd hooks && echo x > pre.sh` ask; a word whose base is certain is measured from that base alone. A written word that names a `for` loop's variable (`for f in .mcp.json; do echo x > $f; done`) is tried with each literal word of the loop's list in its place. This is not precise, and errs towards asking: every landing before a word is tried whatever ran in between, so `cd .claude && ls; cd .. && echo {} > settings.json` asks, though its write lands at the workspace root. **Not recognised, as examples rather than a complete list:** another user's home written as `~someone/x`, a path glued to a short flag as `-C/tmp`, a path in the code of a script file a command runs (`python3 tool.py`), and anything the command computes at run time. Those fall into the fourth and fifth rows, where on Windows and Linux nothing catches them. Widening the recogniser is worth doing when a spelling is cheap to catch; it is never a route back to claiming the first two rows are complete.

  The classifier reports EVERY distinct crossing, in the order the command names them, and `lib/http-router.js` answers from a standing folder grant only when every one is covered AND the request is grantable. **A shell request is never grantable**, because a folder grant says an agent may touch a folder while approving a shell request says a command may run, and everything in the command runs rather than only the part touching the folder. **The exemption in row three is deliberate:** `/dev/null` and the directories interpreters live in appear in a large share of ordinary commands, including every shebang an agent writes into a script, and carding `2>/dev/null` would put a boundary card on ordinary work, which teaches people to click through the one card that matters. It is judged on the POSIX-normalised token, so it holds on a Windows host and so a path climbing out of an exempt directory is still a crossing. Enabling the sandbox also isolates the network, which is why the domain list is deliberately open: with none, every outbound host is refused for shell commands and, unlike a refused write, a refused host produces no retry. A refused write does not guarantee a card either: the retry that raises one is the agent's choice, and it may simply report the failure.

  **The files that decide what runs always ask, in both modes.** Five places in a workspace decide what the runtime starts outside the shell sandbox: the launcher the runtime starts the permission hook through (`.rundock/permission-hook.sh`, or `.cmd` on Windows), which Rundock writes on every open and names in the settings file the runtime is launched with, so whatever it says answers every permission check; `.mcp.json`, handed to the runtime with `--mcp-config`, whose stdio servers start at the next spawn as their own processes; `.rundock/mcp-secrets.json`, which supplies the `env` and `headers` those servers start with, so an `env` such as `NODE_OPTIONS` changes what one runs; the project's `.claude/settings.json`, whose hooks and `env` the runtime acts on for every agent spawned there; and anything under `.claude/hooks/`, the scripts those hooks commonly run. Each is an answer file to the hook, as `.rundock/state.json`, `.rundock/permissions.json` and `.claude/settings.local.json` are (`LAUNCHER_FILES`, `WHAT_RUNS_FILES` and `WHAT_RUNS_DIRS` beside `WORKSPACE_ANSWER_FILES` in `scripts/permission-hook.js`). A write, edit or delete by a file tool, or a shell command that writes, edits or deletes one (a redirect, `tee`, `cp` or `mv` onto it, `sed -i`, `rm`), asks every time with Allow and Deny only, in Notes and Code mode alike; no saved "Always allow" and no folder grant answers it (`crossingCovered` in `lib/workspace/boundary.js` recomputes this from the path); and when Rundock cannot be asked it is refused rather than allowed. **The launcher is the exception, and is refused outright.** Rundock writes it on every open and puts back any other change to it without a card (below), so an Allow could never hold; a write to it, this workspace's or another Rundock workspace's, by a file tool or a shell command, is refused before any card, with a reason, in both modes, as the settings file the runtime is started with is. Reading them is free. A shell command asks only when it can write one (`answerFileWriteWords` in the hook): a redirect or `tee` into it, a copy, install or `dd` onto it, `install -d` naming it, and anything else naming it unless its program is known to only read what it names, so `sed -i` (and macOS `sed -I`), `perl -i`, `rm`, `mv`, `ln`, `touch`, `truncate`, `chmod`, `git checkout` and `git restore` ask, and so do `git add` and `git commit` naming one, while `git diff`, `git log`, `jq`, `diff` and a copy out of one do not. A program with an option that writes a file it is given with no redirect is never taken as a reader: a pager's log file (`less -o`), `sdiff -o`, `tree -o` and `file -C` ask like any program the check does not know, and `tree -o` and `file -C` are not reads in the shared read-only vocabulary either. A command that removes, moves or replaces a folder holding answer files (`rm -rf .claude`, `mv .rundock old`), copies or moves into a folder under an answer file's name (`cp backup/.mcp.json .`), or names a glob that can match one (`rm -rf .claude/*`, `rm -rf .*`, `rm -rf .[!.]*`) asks the same way, with braces expanded as the shell would first (`rm -rf .{claude,rundock}`); the workspace root itself is not such a folder, so `git add .` and `rm -rf *` are judged as before. In code handed to an interpreter, a literal counts as writing one only where the code can write it (`codeWrites` in the hook): as the path given to a call that removes, moves, renames, copies into, makes or writes a file (Python's `os`, `shutil` and `pathlib`, Node's `fs` in its plain, `Sync` and `promises` forms, Ruby's `File` and `FileUtils`, Perl's builtins), called bare or on its module but never as a method of anything else, as the path of an `open` whose mode or flags write, or in a command the code runs (`os.system`, `subprocess`, `child_process`), by itself or through a name it was put in or a loop over one. So `open('.mcp.json', 'w')`, `shutil.rmtree('.claude')` and `fs.rmSync('.claude')` ask, while `open('.mcp.json')`, `readFileSync('.claude/settings.json')`, `print('.claude')`, `dirs.remove('.claude')` and a list of folders a walk skips do not. `git clean -x` and `-X` name no file but remove the ignored `.rundock` folder: Notes mode grades `git clean` destructive, and Code mode asks every time while `.rundock` is in its reach. Not caught, because nothing in the command names the file or a folder holding it: a git command that rewrites tracked files wholesale (`git checkout <branch>`, `git stash`), an archive unpacked over the workspace, a copy of a folder's contents into the workspace root (`cp -a template/. .`, or BSD `cp -R template/ .`), a write made inside a program's own text that is not read as code (sed's `w` command, `awk '{ print > ".mcp.json" }'`), a path that code given to an interpreter builds as it runs rather than names in a string literal, or a script. Nor is a literal with the open mode written into it, as in Perl's two-argument `open(F, ">.claude/hooks/pre.sh")`: the literal is not the file's name, so it matches nothing (the three-argument `open(F, '>', '.claude/hooks/pre.sh')` names the file and asks). Nor is a path code hands to one of its own functions, to a call written without brackets (Ruby's and Perl's), or to a write made through a path object the code did not make from `Path(...)` in the same code. Hooks declared in an agent's or a skill's frontmatter are not among these files either: they live with the agents and skills, which are ordinary workspace files. Paths are compared by their real names, so a case variant on a case-insensitive filesystem, a workspace opened through a symlink and a `.claude` folder kept elsewhere through one all reach the same file; another Rundock workspace's copies (a folder holding `.rundock/state.json`) ask too. The card says what the file decides: for a launcher, where a card is still drawn (a Codex agent's escalation that reaches one), that it starts the permission checks themselves; for the others, that it decides what Rundock or Claude Code runs, outside the sandbox. The hook reads the command a tool call carries, not what a script does once it runs, so a write made by a script, or by code that builds its path as it runs, never meets it: where the operating-system block runs, it refuses a sandboxed write to the launcher, `.mcp.json`, `.rundock/mcp-secrets.json`, the project settings and `~/.rundock-console` however it is made. **Rundock's console folder under home always asks too.** `~/.rundock-console` holds the script Rundock opens in Terminal when a person reconnects Claude Code, so what it says runs outside every sandbox the moment they press the button. A write there, to the folder or anything in it, by a file tool or a shell command (a glob at home that matches it included), asks every time with Allow and Deny only, in both modes, no stored grant answers it, and it is refused when Rundock cannot be asked, wherever the workspace is: with the workspace at the home folder it is otherwise ordinary work inside it (`RUNDOCK_CONSOLE_DIR` in `scripts/permission-hook.js`). A read is judged as before. The detect-and-restore guard does not watch it, so a Codex agent's write there, which never escalates inside a home-folder workspace, is not caught. Behind both, for Claude and Codex turns alike, the detect-and-restore guard (`lib/workspace/answer-file-guard.js`) watches every file the hook names, lists `.claude/hooks/` at every check (up to 64 files, four folders deep) so that a script added during a turn is a change from nothing, and puts back a change Rundock did not make during a turn, offering it on the put-back card. A folder on the way to a watched file that has been swapped for a link is taken away before anything is put back, so a restore never lands where the link points; a link a person had there from the start is kept, or pointed back if it was moved. For a Codex agent, whose writes inside the workspace never escalate, that guard is the only line. `.mcp.json`, the per-user connector file and the hook scripts are edited by hand and by git too, so a change found as a turn starts is taken as the new starting point, as the Claude Code settings files are, and named in a quiet notice in that turn's conversation, since a late write by an agent's background job would stand the same way. A hand edit to one of them made while an agent's turn runs cannot be told from the agent's, so it is put back and offered on the put-back card like one. The launcher is this copy of Rundock's own: a change to it, whether an agent made it or another copy of Rundock open on the same workspace wrote its own, is put back to the one this copy wrote, with no card and nothing said to the agent. A Claude agent's write that a person allowed on the hook's card stands: the Allow marks each answer file the card named, for that conversation, with the content the card showed (a Write's content, or an Edit or a MultiEdit worked out against the file as it stood, a MultiEdit's edits applied in turn), and the guard takes the next matching change during one of that conversation's turns as the new starting point, once, with no second card. A shell command names no content, so its mark covers the path, and only for that command: it is dropped at the check made as that command finishes (the PostToolUse check, where Rundock owns the settings file; elsewhere it lasts until the turn ends), so a later write in the same turn is put back; a mark nothing used ends with the turn, and no launcher write is ever allowed to begin with. Rundock's own writes of these files are made from its server, which neither the hook nor the sandbox judges: the launcher on every open, sound hooks muted in the project settings, and a connector an agent asks for, written into `.mcp.json` only once the person allows it (below). Rundock never writes `.rundock/mcp-secrets.json`; the person does.

  **An Allow on these cards may not take effect for the files Claude Code protects itself.** Claude Code's documentation lists `.mcp.json` and the whole `.claude` folder among its protected paths (code.claude.com/docs/en/permission-modes, "Protected paths"): in `acceptEdits`, the mode Rundock runs it in, a write to one is never approved by the runtime on its own but prompted, its own allow rules do not pre-approve it, and output redirects and `tee` are checked against the same list (code.claude.com/docs/en/permissions). Rundock runs it with nobody at its prompt, so such a write is refused, which is what was recorded when two agents tried to edit `.mcp.json` with their file tools after the person had approved. The documentation lists `cp`, `mv` and `sed` among the commands `acceptEdits` approves on its own, and says writes to protected paths are prompted in that mode all the same. It does not say whether a PreToolUse hook's allow lifts the protection; the refusals recorded for `.mcp.json` happened while Rundock's hook was already answering allow for that in-workspace write, which suggests a hook's allow does not lift it for file tools. So the card for `.mcp.json`, `.claude/settings.json` and the hook scripts says that Claude Code may refuse the change even after it is allowed, rather than promising otherwise. `.rundock/mcp-secrets.json` sits in `.rundock`, which Claude Code does not protect, so an Allow there takes effect; the launcher, also in `.rundock`, is never offered an Allow (above). This is from the documentation, not from running the runtime.

  **A connector an agent asks for is written only once the person allows it.** An agent adds or removes a connector with the `SAVE_CONNECTOR` and `DELETE_CONNECTOR` markers; the window turns each into a message and the server writes `.mcp.json` (`handleSaveConnector` and `handleDeleteConnector` in `lib/protocol/handlers/team.js`). Each message first raises its own permission card through the server's own permission request, naming the server and exactly what it would run (the command and its arguments, quoted as a shell would need them) or reach (its URL), with the names of the environment variables and headers set for it and any header helper it runs. The window grades it high, so it offers Allow and Deny only and no saved allow answers it. Only an Allow a person gave on that card writes: Deny, an allow that came from no card, or no answer before the timeout, which includes no window to ask, writes nothing, and the same marker in a later reply raises a card of its own. Settings has no connector writer of its own: its Connectors tab hands adding one to the guide, which uses the same marker and meets the same card.

  **What Rundock decides for an agent is never inherited.** The permission hook reads Code mode from `RUNDOCK_CODE_MODE` alone, and `RUNDOCK_CONVO_ID` names the conversation it asks for; `getSpawnEnv` in `lib/runtime/claude.js` removes both from the environment Rundock was launched with before setting its own, so a value present at launch can neither put a Notes workspace under Code-mode grading nor give an agent a conversation it does not have. `launchctl setenv`, `unsetenv`, `config`, `load`, `bootstrap` and `submit` change what every program started from then on inherits, Rundock included the next time it is opened from the Dock, or start a program under launchd, so they always ask in both modes: in Code mode they are graded like elevation (`scripts/code-mode-verdict.js`), and in Notes mode they are part of the shared definition of an irreversible command (`isDestructiveShellCommand` in `public/read-only-shell.js`), so the card is graded high, no saved allow answers it, and the hook refuses it when Rundock cannot be asked. Notes mode grades `launchctl` high too when the line does not spell its subcommand: given none, it reads them from standard input (`echo setenv X 1 | launchctl`), and one starting with a quote, `$`, a backtick or a backslash is filled in by the shell. `print`, `list` and `getenv` run as before.

  <!-- boundary-registry-start -->
  **The agent's own folder (`~/.claude`) is graded by persistence, not by location.** A model tool reading anywhere under it raises no card, with one exception. `.credentials.json` is the **secrets registry**: it cards on any access, read or write, in both modes, and no grant, mode or setting silences it, because a credential leak cannot be undone. **Where the operating-system block runs, a write to it is refused by the operating system as well:** the writable-roots list in the OS-guarantee row names `~/.claude` as a whole (the runtime's own bookkeeping lives there), and the block's `denyWrite` list names every path this registry calls a secret, in both runtime homes. On macOS the runtime keeps its live credential in the Keychain and falls back to the plaintext `.credentials.json` only when the Keychain is unavailable, so the deny covers that plaintext fallback and Codex's `auth.json`, not the Keychain item. The deny covers writes only. Reads, which are all that stealing a token takes, are guarded by the permission card alone. The deny list is built from this registry rather than restated, and a test fails if the two differ. Where no block runs (Windows, Linux, or the switch off), the permission card holds the line for writes as well. Writing to `agents/` or `skills/` is **refused outright, not carded**: a pre-existing guard denies the write before it reaches the card, and correctly so, because Rundock reads the *workspace's* agents and skills, never the global ones, so an edit here would land somewhere the app never looks, report success, and change nothing. Writing to any other **persistence surface** (`plugins/`, `commands/`, `hooks/`, `settings.json`, or the global instruction files `CLAUDE.md`, `rules/` and `output-styles/`) **splits by which tool is writing, and the split is the runtime's, not this product's.** A model **file-edit tool** (`Write`, `Edit`, `MultiEdit`, `NotebookEdit`) is **refused outright**: measured against the runtime, it rejects a file-edit write anywhere under `~/.claude` as a sensitive file whatever is approved here, so a card offering to allow one is a promise this product cannot keep, and approving it only to be refused underneath teaches the reader that the card means nothing. Nothing is lost by refusing first, because that write could not land either way, and what the reader wants to change almost always lives in the workspace's own `.claude`, which is the copy Rundock reads. A **shell command** reaching the same path is **not covered by that refusal and still cards**, and is approvable. Approving it lets the command run. Where the operating-system block runs, the block's `denyWrite` list names `settings.json` and the `plugins/`, `hooks/` and `commands/` folders, with `skills/` and `agents/` above, so the sandboxed write is refused whatever the card said, as the runtime's own deny list also refuses it in the releases that carry one. A write to the global instruction files (`CLAUDE.md`, `rules/`, `output-styles/`) is not in the block's deny list and lands once approved, unless the installed runtime's own list refuses it, as the 2.1.259 bundle's does (a static read of the bundle, not a live measurement). Where no block runs, and for a retry outside the sandbox, which cards again, a write to any of them lands. What is stated is what this product does, which is to card the command rather than refuse it, and a test reads the hook's verdict for both families at one persistence-surface path so this paragraph cannot drift from what the hook does. Writing anywhere else in the folder (`projects/`, `cache/`, `paste-cache/`, `downloads/`, `tasks/`, `file-history/`, `shell-snapshots/`, `session-env/`, `history.jsonl`) is free: it is scratch and transcripts, the agent's own furniture, reached freely by the same agent in a terminal. Every one of those names lives in one registry in `scripts/permission-hook.js` (`SECRET_RELATIVE_PATHS`, `PERSISTENCE_SURFACE_DIRS`, `PERSISTENCE_SURFACE_FILES`); a name this paragraph does not carry is not one the registry enforces, a name the registry does not carry is not one this paragraph may claim, and a fail-loud test binds the two in both directions. There is no narrow remembered grant: an earlier design carded the whole folder and then carved a hole back out of it with a folder-scoped grant labelled for one use and stored for a wider one, which is exactly the mismatch a boundary drawn by persistence rather than by location no longer needs.

  **The other runtime's home (`~/.codex`) is graded on the same three tiers, by the same registry shape.** Rundock spawns Codex as well as Claude, and for a long time only one of the two homes was graded: an agent reading its own configuration was silent on Claude and raised a card on Codex, which Rundock's own Connectors tab reads and displays without asking anyone. `auth.json` is the **secrets registry** for this home, the counterpart of `.credentials.json`: it cards on any access, read or write, in both modes, and no grant, mode or named working folder silences it. That tier is not only about noise. Untiered, `~/.codex` was ordinary outside access, so its card offered a standing grant on the whole folder, and anyone who accepted it to stop being asked about configuration would have silenced every later read of the credentials sitting beside it; the secrets tier refuses a folder grant outright, which is why credentials belong in it and why naming `~/.codex` as a working folder does not exempt them either. `config.toml` is this home's `settings.json`: **free to read, cards on write**, together with `prompts/` and the global instruction files `AGENTS.md` and `rules/`. **The global instruction files of both homes are protected in both modes**, because a write to one plants instructions every later session loads, in every workspace, including routines that run unattended; a shell write to one asks every time and is never remembered, and reading them stays free. Everything else in the folder is scratch and is free both ways: the session databases, caches, logs, locks and `history.jsonl` are the runtime's own furniture, reached freely by the same agent in a terminal. Those names live in their own registry rows in `scripts/permission-hook.js` (`CODEX_SECRET_RELATIVE_PATHS`, `CODEX_PERSISTENCE_SURFACE_DIRS`, `CODEX_PERSISTENCE_SURFACE_FILES`), kept separate from the Claude rows rather than merged into them, because a shared list joined onto one home would make `~/.claude/auth.json` a secret and `~/.codex/auth.json` nothing at all. The same fail-loud test binds these to this paragraph in both directions.
  **Two secrets sit in the home folder itself, beside the runtime home: `.claude.json` and `.claude.json.backup`.** The first is Claude Code's user-level state: user-scope MCP servers, whose commands the next session starts outside any sandbox, per-project trust, and account details. The backup carries the same contents. Both card on any access, read or write, in both modes, and no grant, mode or named working folder silences them; a match is at the home folder's root only. The OS-guarantee row's writable roots name `~/.claude.json`, because the runtime writes it continuously, and the block's `denyWrite` list takes it back for sandboxed commands, together with the backup. The runtime's own saves are unaffected: it writes the file from its own process, which the sandbox does not confine, by a temporary file beside it renamed into place under a lock. The runtime reads `.config.json` under `~/.claude` in place of `~/.claude.json` whenever it exists, so that file is in the `~/.claude` secrets registry with the same treatment: denied to sandboxed commands, asked about on every access. These names live in `HOME_SECRET_FILES` in `scripts/permission-hook.js`, and the same tests bind them to this paragraph and to the deny list.

  **The Keychain holds the runtime's live sign-in token on macOS, and only the card guards it, so a command that reads or changes a Keychain item asks every time, in both modes.** The operating-system row cannot help here: the sandbox profile allows the Keychain service, because the runtime itself signs in through it, so a sandboxed command can run `/usr/bin/security`, search the Keychain and read an item. Measured rather than assumed: a lookup of a made-up item name from inside the sandbox came back "The specified item could not be found in the keychain", a search that ran rather than one that was blocked. The check runs only on macOS; on another host `security` is some other program and is graded as before. `judgeSecurity` in `scripts/code-mode-verdict.js` decides it, inverted the way the `find` rule is: every `security` subcommand asks except `help`, `error`, `show-keychain-info`, `verify-cert`, `find-identity`, and `list-keychains`, `default-keychain` and `login-keychain` without `-s` (with it they set the search list or the default), matched by exact name so a shortened or misspelled subcommand asks too. A password lookup without `-w` or `-g` asks: it prints an item's account and service rather than the secret, and those are what the next command needs to find a token. `-i` and `-p`, which read further commands from stdin, ask. The line is read by the Code-mode verdict's own reader, so the command is found wherever it sits: in a chain, a pipe, a subshell or group, a substitution, after `sudo` or `doas` (read past their options), `nice`, `time`, `env VAR=…`, `command`, `exec` or `xargs`, through `find -exec`, inside `bash -c` or `sh -c`, in a here-document or here-string a shell reads, and on a line whose here-document never ends. That line asks as one Rundock cannot read, and is still checked for the Keychain as a conservative reading: its command lines, with the unfinished body taken as data to the end of the text unless a shell reads it. What `sudo` or `doas` runs and an unfinished here-document are read for the Keychain alone, with no disk or git facts, since the line asks either way; elevations are read through eight deep, so a Keychain command under more of them asks as elevation in Code mode and is carded as before in Notes mode. The rules apply on macOS alone, and the hook judges for the host it runs on, except under one test-only seam (`RUNDOCK_TEST_PLATFORM`, read only when `RUNDOCK_TEST_SEAMS` is 1) that lets the end-to-end suite prove the Mac's rules on any host. The seam moves that check alone, never path handling or the checks on deletes; the hook ignores it when it runs as the app's Electron binary, as it always does in the app; and `getSpawnEnv` removes both names from the environment Rundock starts agents with, so a value set in Rundock's own launch environment never reaches a hook. Among reasons to always ask, the Keychain is the one the card names, and the first other reason on the line is kept beside it: a line that also deletes work git has never saved says so on the card, and the refusal adds that part of it cannot be undone. Notes mode has no verdict of its own, so the hook asks `keychainVerdict` that one question, reading disk and git facts only for a line that reaches the Keychain, and sends the answer as the request's verdict; every other Notes-mode request is graded as before. Either way the card says "This reads or changes a password or key stored in your Mac's Keychain", offers Allow and Deny only, is drawn ahead of any saved "Always allow" whatever word the line starts with, offers no folder to remember, names no setting that would stop it, and when Rundock cannot be asked the hook refuses the command. Codex escalations carry the same verdict in both modes and offer no folder either (`lib/runtime/codex-approval.js`). **What it cannot see, in two groups.** These still ask in Code mode, as commands Rundock cannot read: `eval`, a `case` or a function definition, a wrapper the reader does not model (`caffeinate`, `arch`, `script`, `stdbuf`, `watch`, `parallel`, `env -S`), a program name in quoting it does not follow such as `$'security'`, and a program name that is a glob or a variable. These run with no card in Code mode: code an interpreter is given (`python3 -c`, `node -e`, `perl -e`, `ruby -e`, `osascript -e`), a script (`./k.sh`, `bash script.sh`, `bash < script.sh`, `source`), `security` under another name (a symlink, a copy, an alias, `xcrun security`), and text piped into a shell (`echo '…' | sh`). In Notes mode both groups are carded as before, where a saved "Always allow" for the line's first word can still answer them. The flow is driven end to end, in both modes, through the real hook, server and card in `test/integration/keychain-approvals.test.js`, and every position and subcommand in process in `test/unit/keychain-commands.test.js`.

  **A workspace can name additional folders its agents work in, and naming one never reaches the tiers above.** The folders are set in Settings under Workspace, stored with the workspace, and passed to each agent as it is spawned; a named folder is compared by the same containment rule the workspace root already uses, so everything beneath it is covered, including directories created later. Naming a folder is a statement about where a team works, not a grant: it is not remembered per card, not per agent, and it says nothing about any folder that was not named. **It stops at the runtime's own home.** A named folder that contains `~/.claude`, the home directory being the obvious one, does not make anything under `~/.claude` inside: the secrets registry still cards on every access, a persistence-surface write is still refused or carded exactly as above, and both outright refusals still apply. Only the workspace a person deliberately opened is exempt from those refusals, and a named folder is not that act, because its whole value is covering folders nobody enumerated. `namedFolderCovers` in `scripts/permission-hook.js` is the single place that rule lives, and a mutation row fails if it is removed.

- **"Rundock itself contacts only GitHub, and sends none of the user's data there."** The desktop app's update check goes to GitHub releases through `electron-updater`, on launch (`setupAutoUpdate`) and from the Check for Updates menu item, both in `electron/main.js`. Packages are fetched from `https://github.com/<owner>/<repo>` with `git fetch` and `git ls-remote` (`lib/packages/extension-source.js`) when one is added, checked for updates or updated. Neither request carries workspace content. The dependency footprint is three production packages (`package.json`); the runtimes (Claude Code, Codex CLI) are separate tools you installed and authenticated yourself, spawned as subprocesses by `spawnClaude` (`lib/runtime/claude.js`) and `getCodexAppServer` (`lib/runtime/codex-glue.js`).
- **"Agents cannot impersonate teammates."** The off-roster delegation block lives in the delegation interception path (`server.js`, search for the blocked-handoff notice); the orchestrator-runtime enforcement is in agent discovery.

## What Rundock does NOT do

- **No backend service.** Rundock runs entirely on your machine. There is nothing to deploy and no account to create.
- **No database as a source of truth.** Persistence is JSON files in `.rundock/` and Claude Code's own JSONL transcripts. The one SQLite file (`search-index.db`, behind universal search) is a derived, disposable index rebuilt from those sources: nothing to migrate, nothing to back up, nothing lost if it is deleted. It uses Node's built-in `node:sqlite`, so it adds no dependency.
- **No telemetry.** Rundock does not phone home, does not log usage to a remote service, does not collect crash reports. The three-dependency footprint makes this easy to verify.
- **No outbound network calls from Rundock itself beyond GitHub.** The desktop app checks GitHub for its own updates, and packages are fetched from GitHub when added, checked for updates or updated; none of the user's files, agents or conversations go with either. Every other external connection belongs to a runtime: Claude Code to Anthropic's API, Codex to OpenAI's, and any connector to its own service. Rundock does not make HTTP requests to Anthropic or OpenAI, does not handle API keys, and does not see your Claude credentials.
- **No agent-format reinvention.** Agent files use Claude Code's standard format with optional Rundock extension fields. An agent file written for Rundock works in plain Claude Code; an agent file written for Claude Code works in Rundock with reduced UI affordances. See AGENTS.md.
