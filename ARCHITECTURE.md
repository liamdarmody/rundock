# Rundock architecture

Rundock is a local Node.js server that exposes a vanilla-JS browser client over WebSocket and orchestrates runtime subprocesses (Claude Code by default; optionally the Codex CLI) to do the actual AI work. There is no cloud component, no server-side database, and no build step. The whole stack runs on your machine and reaches each provider only through its own CLI (Anthropic via Claude Code, OpenAI via Codex), which you authenticate yourself.

This document describes the process model, the workspace directory layout, and the codebase, in enough detail that a contributor can navigate the source after reading once. Implementation detail is left to the code; this document covers shape, boundaries, and where to look.

## The process model

Rundock has three classes of process at runtime.

```
+---------------------+        WebSocket         +---------------------+
|                     |  <-------------------->  |                     |
|   Browser client    |                          |   Node.js server    |
|   (public/app.js)   |   HTTP for assets and    |   (server.js)       |
|                     |   permission decisions   |                     |
+---------------------+                          +----------+----------+
                                                            |
                                                            | spawn / stream-json
                                                            v
                                              +-----------------------------+
                                              |    runtime subprocesses     |
                                              |   (one per active agent)    |
                                              +-----------------------------+
```

### The browser client

The browser is the visual interface. It renders the org chart, the conversation panel, the sidebar of past conversations, the file browser, the settings drawer, and the permission cards that pop up when an agent wants to run a tool. It holds no authoritative state. Reload it and the server still owns every conversation, every transcript, every running subprocess.

The client opens a single WebSocket to the server on load and uses HTTP for static assets and a small number of synchronous endpoints (workspace picker, permission decisions, agent listing). All ongoing conversation traffic flows over the WebSocket.

How `public/` is put together, and why it has no build step, is its own page: [CLIENT-ARCHITECTURE.md](docs/CLIENT-ARCHITECTURE.md). Read it before changing anything in `public/`.

### The Node.js server

`server.js` is the single server entry point. It does seven things, in roughly this order of importance.

1. **Discovers agents and skills** by reading the workspace directory (`.claude/agents/`, `.claude/skills/`, `System/Playbooks/`). See `discoverAgents` and `discoverSkills`.
2. **Spawns and manages Claude Code subprocesses.** Each active conversation has at most one running Claude Code child process at a time. The server tracks them in a `processes` map keyed by conversation ID.
3. **Bridges browser and Claude Code** by translating WebSocket messages from the client into stdin writes on the right subprocess, and by parsing the subprocess's stream-json stdout back into client-facing events.
4. **Intercepts delegation** so that when an orchestrator emits an Agent tool call, the server kills the orchestrator process, spawns the specialist with the right context, and streams the specialist's output to the client under the specialist's identity. See the next section.
5. **Persists conversation state** to `.rundock/` in the workspace (conversations index, transcripts, child PIDs, settings).
6. **Runs a lightweight scheduler** for routines defined in agent frontmatter. Every minute, it checks each agent's routines and invokes any whose schedule has come due.
7. **Mediates tool permissions.** Claude Code's PreToolUse hook calls back to the server over HTTP for any tool call that needs approval; the server forwards the request to the browser as a permission card and returns the user's decision to Claude Code.

**Who may drive it.** The server listens on loopback only (`HOST` in `server.js`). Every request then passes two checks before any route runs. `lib/local-origin.js` refuses a foreign `Host` (DNS rebinding) and a foreign `Origin` on a write or a WebSocket upgrade (other web pages). `lib/auth/index.js` then asks one question, `authenticate(req, port)`, of every WebSocket upgrade and every HTTP route except the page's static files, the two routes a browser uses to trade the printed link's code for a session token, and the permission hook's two routes: does this come from Rundock's own window? The desktop window carries the launch key in a header its main process adds (`electron/window-key.js`), and the desktop server accepts nothing else. A browser from source opens the printed link, whose one-time code (good once, for fifteen minutes; a link is printed only at start and when Enter is pressed in the terminal) the page trades for a session token kept in its own origin's storage and sent as a header and in the WebSocket handshake, never as a cookie; pictures and PDFs use a separate cookie that opens only those files. Tokens are kept as fingerprints, bound to their port and expiring. The launch key is made in memory at launch and never written to disk, the environment, a URL, the HTML or a log; the printed links hold only codes, which a terminal or a service journal may keep after they are dead. The hook's routes take a per-agent token instead, bound to that agent's conversation, so an agent can ask for a card in its own conversation and collect its own notice and nothing else. Two of the closed routes are privileged on the machine itself: the chat's reconnect card, when Claude Code's session has expired, asks the server to open a console running Claude Code's own login command, `claude auth login` (`POST /api/claude/reconnect`; only on Claude Code 2.1.41 or later, which first has it, so an older version or one whose version was never probed runs `claude` bare) and, when the person says they have finished, to run the one short turn that says whether it is connected again (`POST /api/claude/connection`). That turn runs from the home folder, never the temp folder, because `--print` skips the trust prompt and on Linux the temp folder is shared with every account; and only a failure whose words are a sign-in failure marks Claude Code signed out, while any other says the check could not tell. The desktop app opens the same console through its main process instead, answering only the main window's own top frame (`fromMainFrame`), and `lib/runtime/claude-console.js` holds the command per platform for both, behind one gate they share: one console opens at a time, and an ask in the few seconds after one opened is answered by that window rather than opening another. Only fixed words go on its command line besides the path to Claude Code, and a path the line cannot hold opens no console at all: one with a line break or NUL anywhere, or on Windows one with `&`, `^` or `%`, which the outer cmd would read. The answer is then that no console can open here, so the card shows the step to run by hand rather than a "Try again" that cannot work. On macOS, where Terminal runs the file it is opened on and takes no words after it, and AppleScript would raise an Automation prompt, the console is a two-line script of those fixed words, written first under the home folder in a folder only that account can use, removed and made again by exclusive create so it is never written through a link. Neither route answers an agent or the hook's token. Server-side writes into the workspace also refuse to leave it through a link (`lib/workspace/link-safe-write.js`). A remote client would use the same `authenticate` with a token issued by pairing, and must ship with transport security; the bind stays on loopback until then.

The server uses Node's native `http` module and the `ws` library for WebSocket. The runtime dependency surface is intentionally small: three production dependencies (`ws`, `marked`, and `electron-updater` for the packaged app's auto-update).

### The desktop app

The desktop app is the same server and the same client in an Electron shell. `electron/main.js` starts `server.js` inside the Electron process on a port the OS assigns, and opens one window on it with `electron/preload.js`, which gives the page the few things only the desktop can provide: the native folder picker, storage that lasts between launches, update notices and window chrome. Everything else behaves as it does in the browser.

**Advanced settings.** Environment variables the desktop app reads at launch. Most people never need them.

| Variable | What it does |
|---|---|
| `RUNDOCK_USER_DATA_DIR` | Runs the app on a profile of its own, kept in the folder given (an absolute path), instead of the usual one. That profile has its own single-instance lock, stored settings, setup record and update record, so a second copy can run beside the one already open, for example against a throwaway workspace. A relative path stops the app at launch rather than falling back to the usual profile. See `electron/user-data.js`. |

### Runtime subprocesses

Every conversation that is actively producing tokens has a runtime child process attached to it. For Claude Code agents (the default), Rundock spawns `claude` configured to read from the workspace directory, with the workspace's `.mcp.json` for MCP servers (merged with the per-user credentials in `.rundock/mcp-secrets.json` where there are any: see MCP credentials, below), with the workspace's `.claude/settings.local.json` for hooks, and with the agent's name passed so Claude Code loads the right system prompt from `.claude/agents/<slug>.md`. Before starting the copy of `claude` it found, Rundock reads that copy's version, and below 2.0.59, the first release that accepts every flag Rundock passes (the table is in `lib/runtime/claude-floor.js`), it starts nothing and says in the conversation, or in the routine's run record, which copy it found, the folders the desktop app puts first on PATH, in order (listed once, in `lib/runtime/claude-folders.js`), and to update that copy or install a current one with the native installer, whose folder is first.

Agents with `runtime: codex` run on the official Codex CLI instead, through ONE long-lived `codex app-server` process shared by the whole server (spawned lazily on the first Codex turn, supervised with restart-on-crash by `codex-appserver.js`). Each Codex conversation is a thread on that process and each message a streamed turn, with conversation continuity through thread resume and the agent's instructions carried in the first-turn prompt (Codex has no `--agent` equivalent). Codex agents use Codex's own sandbox (workspace-write, approvals on-request); sandbox escalations arrive as per-action approval requests that render as Rundock permission cards. The orchestrator always runs on Claude Code (delegation works through the Agent tool in Claude Code's stream, which Codex does not have). Environment detection and failure classification live in `codex.js`.

The subprocess speaks **stream-json** on stdout: a sequence of newline-delimited JSON events (assistant tokens, tool calls, tool results, system events). The server reads this stream line by line and forwards relevant events to the browser as WebSocket messages.

Every message reaches an agent on its process's stdin, and a process can stop before the server has heard that it stopped: Claude Code refuses a resume and exits before reading anything, or the process crashes or is ended. **A write to a stopped process is logged and handled by that process's close, and never ends the server.** Each process's stdin is given its error handler once, where the process is started (`lib/runtime/child-stdin.js`, called from `spawnClaude` in `lib/runtime/claude.js` and from the Codex app-server's spawn in `codex-appserver.js`), so no write site needs one of its own. The handler logs one line per failed write, naming the process and the error, and does nothing else: the process's close then ends its turn or its delegation exactly as it does for any process that stops. Pinned by `test/unit/doc-claims.test.js`, and every write to a child's stdin is held to those two start paths by `test/unit/child-stdin-inventory.test.js`.

The subprocess's working directory is the workspace. Its file access, tool availability, and permissions are governed by Claude Code itself, not by Rundock. Rundock can only configure the spawn arguments and intercept the streamed output.

### Conversations: resume vs spawn fresh

Each Rundock conversation has its own Claude Code session ID. When a user opens a past conversation and sends a new message, the server spawns Claude Code with `--resume <sessionId>` so the model picks up the existing transcript from Claude Code's JSONL file. When a user starts a new conversation, the server spawns a fresh Claude Code subprocess and records the new session ID for next time.

Resume works because Claude Code persists every session as a JSONL transcript in the user's home directory (see The .rundock workspace directory, below). Rundock does not store conversation message content itself; it stores enough metadata to find and resume each session.

Claude Code removes old session files on its own schedule, so a stored id can outlive its session. Resuming one is refused with "No conversation found with session ID". Every resume path recognizes that refusal in one place (`lib/runtime/missing-session.js`): the id is forgotten from the conversation's stored state and from every open window, the store will not take it back from a window that saves it again, and the turn starts again in a fresh session with a short notice naming the agent. A delegate is briefed as arriving; an orchestrator is given its handback and the conversation so far, also as arriving. Anything the person sent while the refused process was starting follows into the fresh one, in order. A resume that cannot be started again where it failed says what happened and asks the person to send again. The raw refusal is never shown, even when it reaches the pipe in pieces. Only a session the server names is ever forgotten by the window: a notice that names none leaves every stored session alone.

### Delegation: how the orchestrator hands off to a specialist

The delegation handoff works in five steps:

1. The orchestrator's Claude Code subprocess emits an Agent tool call event in its stream-json output, with the target specialist's slug as the argument.
2. The server detects the Agent tool call and treats it as a handoff signal. It kills the orchestrator's subprocess with `SIGKILL` so no further output reaches the client under the orchestrator's identity.
3. The server emits a `system: agent_switch` event to the client. The browser updates the conversation header and sidebar to show the specialist as the active agent.
4. The server spawns a new Claude Code subprocess with the specialist's slug. It passes a context block containing the conversation transcript so the specialist sees what happened before they were called.
5. The specialist's stream-json output flows back through the same bridge as the orchestrator's. The specialist signals completion with a `RUNDOCK:COMPLETE` or `RUNDOCK:RETURN` marker in its final response. On COMPLETE the work is done; on RETURN the server spawns the orchestrator again so it can pick up where it left off or hand off elsewhere.

This interception model is what makes "delegation that happens in front of you" visible. The agent name in the conversation header changes mid-stream, the sidebar updates, and the user sees specialists arrive without lifting a finger.

## The .rundock workspace directory

When Rundock first opens a workspace, it creates a `.rundock/` directory at the workspace root. This holds Rundock's own session state. It is added to `.gitignore` automatically on creation.

Contents:

| File or directory | Purpose |
|---|---|
| `state.json` | Workspace-level settings: setup completion flag, workspace mode (`notes` or `code`; a `knowledge` written by an earlier release reads as Notes, through `lib/workspace/mode.js`), whether agents are kept inside the workspace (`sandboxSwitch`), version. |
| `conversations.json` | Index of every Rundock conversation: ID, title, owning agent, last Claude Code session ID, timestamps. |
| `transcripts/<convoId>.json` | Lightweight conversation transcript for fast UI replay (role, agent, text). Capped to keep file size reasonable. |
| `child-pids.json` | Running Claude Code subprocess PIDs, used to clean up zombie processes on server restart. Each record carries the command it was spawned as, so a pid the OS has since recycled onto an unrelated process is not signalled. Not every platform can read a command line, and where none can be read the record is assumed to be ours rather than discarded: `pidRecordAlive` in `lib/runtime/claude.js` documents which sources exist, what each costs, and what that assumption gives up. |
| `search-index.db` | SQLite FTS5 index behind universal search (plus its `-wal`/`-shm` journal files). A **derived artifact**: delete it and the next workspace open rebuilds it from the files and transcripts it indexes. Never a source of truth. See Universal search, below. |
| `mcp-secrets.json` | Optional, and written by you rather than by Rundock. Per-user MCP credentials keyed by server name: the values that must not travel with the shared `.mcp.json`. See MCP credentials, below. Its `env` sets what each server starts with, so an agent's change to it always asks. |
| `mcp-runtime.json` | The shared `.mcp.json` with those values merged back in, written owner-only and pointed at by `--mcp-config`. A **derived artifact**, like the search index: regenerated before every spawn, safe to delete, and absent entirely unless `mcp-secrets.json` supplies a value. |
| `permission-hook.sh` | The launcher the runtime starts the permission hook through (`permission-hook.cmd` on Windows), rewritten on every open and named in `.claude/settings.local.json`. Whatever it says answers every permission check, so an agent's change to it always asks: see the files that decide what runs, under "An agent stays inside your workspace", below. |

What does **not** live in `.rundock/`:

- **Full message content.** The complete model output, tool calls, and tool results live in Claude Code's own JSONL transcripts at `~/.claude/projects/<projectHash>/<sessionId>.jsonl`. Rundock keeps a slimmer copy in `transcripts/` for UI replay, but the source of truth for the actual conversation is Claude Code's JSONL. A reopened conversation's history is rebuilt from both (`lib/protocol/handlers/history.js`): the JSONL supplies the words, and the transcript orders and attributes them from the moment it began, which is what keeps a specialist's replies interleaved with the orchestrator's rather than grouped by session file. A conversation with no session left, because Claude Code removed every one, is rebuilt from its transcript alone. A conversation whose earlier history is in its JSONL alone (imported, seeded, or older than transcripts) starts a transcript with its first new message; the lines from before that message are shown ahead of the transcript's turns, in time order across session files, each once, and are never matched to a later turn. Rundock's own lines are never shown or counted, wherever they fall: the prompts it sends agents, catch-up headings and all, and the orchestrator's `<silent>` sentinel. One list says which they are (`lib/delegation/rundock-lines.js`), read by the history and by the conversation list's message counts alike. Claude Code's own notes are hidden as Claude Code itself hides them: the summary it leaves when it compacts a session always, a meta line (a reminder, hook context, a skill body, a task notice, a command's expanded prompt) unless a person or a peer sent it, a task notification, and a line its transcript view alone shows. Only the person's side is judged; a reply is always shown. A reply carrying the `<silent>` sentinel is shown as it was live: hidden where it was parked, and otherwise without the sentinel. Earlier history is read in full however long it is; the transcript's turns are matched among each session file's newest 999 lines, because each turn is looked up by a scan and a whole long file would make that grow with the square of its length.
- **Theme and UI preferences.** These live in browser local storage. They do not sync between machines.
- **Agent and skill files.** These live in the workspace under `.claude/agents/` and `.claude/skills/`. Rundock reads them; it does not store them in `.rundock/`.

This split matters because it means Rundock's persistence layer is small and easy to reason about. The expensive thing (every token of every conversation) is owned by Claude Code, which Rundock does not need to replicate or back up.

### MCP credentials

`.mcp.json` is shared and `.rundock/` is not, and that difference is the whole of this. MCP servers commonly take an API key as a literal value, and `.mcp.json` sits at the workspace root with nothing excluding it, so on a workspace shared by repository the key reaches every clone and stays in the history from the first commit, where deleting the file afterwards does not remove it. The values can instead go in `.rundock/mcp-secrets.json`, keyed by server name:

```json
{ "notion": { "env": { "NOTION_API_KEY": "ntn_..." } } }
```

`lib/workspace/mcp-secrets.js` merges the two before every spawn and `getBareArgs()` points `--mcp-config` at the result. Its header comment carries the reasoning; four properties are worth knowing here.

- **Only `env` and `headers` are taken from the per-user file.** It supplies values and can never change which servers exist or the command named for one, so `.mcp.json` stays the single answer to what the workspace has. An `env` value can still change what that command does (`NODE_OPTIONS`, say), which is why an agent's change to the file always asks.
- **A literal credential left in `.mcp.json` still works.** Where no per-user value applies, the shared path itself is what gets passed, so a workspace that has not moved anything spawns exactly as it did. Moving a key is opt-in, and nothing scaffolds the per-user file or prompts for it.
- **The merged file wins over the copy Claude Code finds by itself.** Claude Code also discovers `.mcp.json` from the working directory, so a server named in both has two definitions. Measured against claude 2.1.245 with project-scope servers explicitly enabled: the `--mcp-config` entry is the one that starts, and only one server process starts.
- **It is replaced by rename, never rewritten in place.** The path is resolved again on every spawn, so a truncate-then-write would let an agent starting at that moment read a half-written config and come up with no MCP servers at all.

The environment was the alternative and was rejected. Claude Code expands `${VAR}` inside `.mcp.json`, so injecting the values into the spawn environment would need no file at all, but the environment of a spawned process is inherited by every child it starts: every other MCP server, and every shell command an agent runs. That would show one server's credential to all of them. An inline `--mcp-config` JSON string was rejected for the same kind of reason: it puts every credential in a command line, which on Linux any local user can read.

## File system layout per workspace

A workspace is any directory that contains, or is intended to contain, Claude Code agents. Rundock looks for these specific things:

| Path | Required | Purpose |
|---|---|---|
| `CLAUDE.md` | Recommended | Workspace-level rules and context. Loaded by Claude Code with every spawn. Used to derive the default agent identity if no agent files exist. |
| `.claude/agents/*.md` | Yes for a Rundock-ready workspace | Agent files. One file per agent. See AGENTS.md for the frontmatter reference. |
| `.claude/skills/<slug>/SKILL.md` | Optional | Skills the agents can use. Rundock matches them to agents either by explicit `skills:` frontmatter or by body-text mention of the slug. |
| `System/Playbooks/<slug>/PLAYBOOK.md` | Optional | Alternative skill location, scanned alongside `.claude/skills/`. Used by workspaces that pre-date the standard skill location. |
| `.claude/settings.local.json` | Optional | Hooks and per-workspace Claude Code settings. Forwarded to spawned subprocesses. |
| `.claude/settings.json` | Optional | The project's Claude Code settings, loaded for every agent spawned here. The hooks it names, and the scripts under `.claude/hooks/` they commonly run, are started by the runtime itself, so an agent's change to any of them always asks. |
| `.mcp.json` | Optional | MCP server configuration. Forwarded to spawned subprocesses. Shared with anyone the workspace folder is shared with, git included, so credentials belong in `.rundock/mcp-secrets.json` instead: see MCP credentials, above. Its stdio servers start as their own processes, so an agent's change to it always asks. |
| `.rundock/` | Created on first run | Rundock's own session state. See above. Auto-added to `.gitignore`. |

A workspace can also contain any other user files at the root or in subfolders. Rundock does not require a particular folder layout outside of the paths above. The browser's file panel reads from the workspace root and respects `.gitignore`.

**Production dependencies:** `ws` for WebSocket, `marked` for markdown rendering in conversation messages, `electron-updater` for the packaged app. Nothing else.

**Build artefacts:** none. `npm start` runs `node server.js` directly. There is no transpilation, no bundling, no minification step. If you change a file in `public/`, reload the browser. If you change `server.js`, restart the server.

**Where things are:**

- Agent discovery: `discoverAgents` in `lib/agents/discovery.js`. Reads `.claude/agents/*.md`, parses frontmatter, classifies each agent as `onTeam` (has `order`), `available` (has `type` but no order), or `raw` (neither, a bare Claude Code agent).
- Frontmatter parsing: `parseAgentFrontmatter`, `parseCapabilities`, `parseRoutines`, `parsePrompts`, `parseSkills` in `lib/agents/discovery.js`. Hand-rolled YAML subset, intentionally lenient.
- Skill discovery: `discoverSkills` in `server.js`. Scans both `.claude/skills/` and `System/Playbooks/`. Matches skills to agents via the explicit `skills:` array first, then falls back to body-text scanning for the slug.
- Subprocess spawn: `lib/runtime/claude.js`, which owns `getBareArgs()` for workspace context flags and `getSpawnEnv()` for environment variables (workspace mode, conversation ID). Codex spawns go through `lib/runtime/codex-glue.js`.
- Delegation interception: `lib/delegation/engine.js`. The interception happens inside the stream-json line handler; `lib/delegation/markers.js` holds the marker grammar and `lib/delegation/state.js` the scope-return bookkeeping.
- Markdown editor in the client: `public/views/files.js`, which owns the Tiptap lifecycle. Used for inline editing of agent files, skill files, and other markdown.
- Search engine: `search.js` (the whole file; its header comment records the design decisions). Server wiring: `ensureSearchEngine`, `reconcileSearchBeforeQuery`, `runUniversalSearch` in `server.js`. Client palette: `public/views/palette.js`.

## Delegation interception, briefly

Mechanically, the orchestrator-to-specialist handoff is a kill-and-respawn:

1. Orchestrator subprocess emits an Agent tool call.
2. Server detects it, kills the orchestrator process with `SIGKILL`, persists the orchestrator's last response to the transcript before the kill takes effect.
3. Server emits an `agent_switch` event over the WebSocket. The client redraws under the specialist.
4. Server spawns the specialist subprocess with the conversation history attached as the initial context.
5. Specialist runs to completion, emits `RUNDOCK:COMPLETE` or `RUNDOCK:RETURN`. On RETURN, the server spawns the orchestrator again so the conversation can continue.

The key design choice is that delegation looks like a real handoff to the user, not like a function call. The specialist runs in its own subprocess with its own system prompt and its own slice of context. The orchestrator does not stay alive while the specialist is working.

## Universal search, briefly

Universal search (the Cmd+K palette) queries four corpora: workspace files, conversations, agents, and skills. Files and conversations are indexed in SQLite FTS5 (`search.js`, using Node's built-in `node:sqlite`: no native dependency); agents and skills are tiny corpora filtered in memory at query time, so they can never go stale.

The things worth knowing that no single file states:

- **The index is a derived artifact.** `.rundock/search-index.db` rebuilds from workspace files and Claude Code's JSONL transcripts. There are no schema migrations: a `SCHEMA_VERSION` bump or a corrupt file deletes the database and rebuilds. Deleting it by hand is always safe.
- **Four reconcile triggers** keep it fresh: workspace open (`ensureSearchEngine`, synchronous full pass), every search (`reconcileSearchBeforeQuery`: conversations always, files behind a 2-second TTL), the `save_file` handler (immediate single-file index), and the end of every agent turn (`appendTranscript` → `noteSearchConversationActivity`).
- **Claude Code's JSONL stays the source of truth for conversations.** The indexer reads deltas past a per-session byte offset (append-only files make this safe); each session's delta lands in one transaction so a crash can never leave duplicate rows.
- **Session ownership is mark-authoritative.** A session's `session_marks` row decides which conversation owns it; `conversations.json` order is not trusted (new entries are unshifted to the head, so order-derived ownership would flip).
- **The grep fallback.** On runtimes without `node:sqlite` (Node 20/21), a capability probe routes every query to a bounded grep path instead. Search degrades; it never hard-fails. `RUNDOCK_SEARCH_DISABLE_SQLITE=1` forces this path for testing.
- **Trust boundary:** user queries never reach FTS5 as syntax (the sanitiser emits only quoted terms), and snippets carry control-character highlight markers that the client swaps for `<mark>` only after HTML-escaping.

The engine is exercised by `test/unit/search-*.test.js` (including a 10k-message performance suite) and `test/integration/search*.test.js`.

  **The card is a best-effort check over common spellings, and cannot be otherwise.** `scripts/permission-hook.js` canonicalises both sides of every comparison first (real paths through the filesystem, an unborn target through its nearest existing ancestor), so an inside path spelled through a symlink, a `/private` alias, or a case variant on the default case-insensitive filesystem is inside however it is written, which retired a class of false cards on symlink-synced workspaces. It classifies file tools by their path field, and shell commands (`Bash`, `PowerShell`) by two signals: the runtime's `dangerouslyDisableSandbox` retry flag, which is the operating system reporting a crossing it already refused, and paths recognised in the command text. The second reads a shell command without running it, and shell is a programming language: a target can be assembled, substituted, or spelled in a form nothing anticipated. Recognised today are absolute POSIX paths, drive letters, UNC names, `..` traversal on either separator, `~`/`$HOME`/`$env:USERPROFILE`/`%USERPROFILE%`, and any of those written after an `=` in a flag value or assignment, whether bare or quoted. On macOS and Linux an absolute literal is a place only when its first folder exists on this machine, so a route, a URL path or a pattern such as `'/health'`, `'/docs/intro'` or `'/+'` is text while `/etc/…`, `/tmp/…`, `/var/…` and a home folder are not. Everything else in a here-document is read word by word as commands: a body fed to a shell or to any other command, data for a script (`python3 tool.py <<EOF`), a shell script written to a file, backticks and Perl's and Ruby's command quotes inside the code, and the substitutions an unquoted delimiter's body runs as it expands. A string handed to a shell with `-c` (`sh`, `bash`, `zsh`, `dash`, `ksh` or `fish`, named by a path or after `env`, `exec`, `command`, `nohup`, `nice`, `time`, `sudo`, `doas`, `timeout`, `gtimeout`, `xargs` (BSD's and GNU's options alike), `stdbuf`, `ionice`, `caffeinate`, `npx` or `uv run`, past their options and `timeout`'s duration) is read as commands, as a here-document fed to a shell is, and so is what it runs in turn: a shell's `-c` inside it, and its here-documents and code, a few levels deep. Relative paths are measured from where the command runs: the working directory the runtime reports, moved by a single literal `cd` that opens the command, or by one partway through an `&&` chain for the words joined to it, into a folder whose real path, through any link, is inside the workspace or a working folder. Any less certain `cd`, or a `pushd` or `popd` anywhere in the command, leaves the starting folder as the base (a folder change is counted where the shell runs it as a command, so `cd` handed to `grep` as a pattern is not one), and a `cd` into a link that leads outside is reported as a crossing. A credential file in the secrets registry is looked for from wherever the shell can be when the word runs, for every word and not only a written one, because the sandbox refuses only writes and a read of one has nothing beneath the card: `cd ~/.claude && cat .credentials.json` is that file. A literal `cd` replaces the folders before it when only `&&` joins it to the word, whether or not its folder is there yet (an earlier command can make it), since if it fails the word never runs, and is added to them across `;`, a new line or anything else, since a `cd` that fails (no permission, or a folder the sandbox will not enter) leaves the shell where it was. The shell starts in the folder the runtime reports for the command. `builtin cd` and `command cd` move it as `cd` does, `cd -` goes back to the folder before the last move, and a `cd` with nothing after it lands at home. Listing names (`ls -R`, `du`, `find` without an action, `rg --files` and `rg --type-list`, which open no file) stays free, unless the names go on to `xargs`, which reads each one; `rg -l` reads the files to know which match, and asks. Code handed to an interpreter that walks the folder itself (`python3 -c "shutil.copytree(...)"`) is not read this way: the literal `~/.claude` there is a place, and reading a place there is free, so that is a known gap. So are names handed on the input to a program other than `xargs` that opens them (`find ~/.claude | cpio -o`, `tar -T -`, or a `cpio -o` or `-p` run in a runtime folder, which opens the names it is given from there), an archive entry with an absolute name, which GNU's `cpio -i` writes where it names, and a reader run after a `cd` this cannot follow (to a variable, or inside `$( )`) or a folder change made by `env -C` or `sudo -D`, which is judged from where the command started. `ack -f`, `ack -g` and `ag -g` list names but still ask, which errs towards asking. On a Windows host this is the same code with that platform's own path rules; the Windows shell the tests simulate on macOS and Linux (`winWorld`) does not run the registry matching, and no CI runner is Windows. For the answer files this is not precise, and errs towards asking: every landing before a word is tried whatever ran in between, so `cd .claude && ls; cd .. && echo {} > settings.json` asks, though its write lands at the workspace root. Nor is the reading of a command nested in a shell's `-c` string: it is read one quoting level at a time, so quoting nested deeper than that reading follows can be taken for the shell's own, and such a command can ask though it writes nothing. **Not recognised, as examples rather than a complete list:** another user's home written as `~someone/x`, a path glued to a short flag as `-C/tmp`, a path in the code of a script file a command runs (`python3 tool.py`), and anything the command computes at run time. Those fall into the fourth and fifth rows, where on Windows and Linux nothing catches them. Widening the recogniser is worth doing when a spelling is cheap to catch; it is never a route back to claiming the first two rows are complete.

  The classifier reports EVERY distinct crossing, in the order the command names them, and `lib/http-router.js` answers from a standing folder grant only when every one is covered AND the request is grantable. **A shell request is never grantable**, because a folder grant says an agent may touch a folder while approving a shell request says a command may run, and everything in the command runs rather than only the part touching the folder. **The exemption in row three is deliberate:** `/dev/null` and the directories interpreters live in appear in a large share of ordinary commands, including every shebang an agent writes into a script, and carding `2>/dev/null` would put a boundary card on ordinary work, which teaches people to click through the one card that matters. It is judged on the POSIX-normalised token, so it holds on a Windows host and so a path climbing out of an exempt directory is still a crossing. Enabling the sandbox also isolates the network, which is why the domain list is deliberately open: with none, every outbound host is refused for shell commands and, unlike a refused write, a refused host produces no retry. A refused write does not guarantee a card either: the retry that raises one is the agent's choice, and it may simply report the failure.

  **The files that decide what runs always ask, in both modes.** Five places in a workspace decide what the runtime starts outside the shell sandbox: the launcher the runtime starts the permission hook through (`.rundock/permission-hook.sh`, or `.cmd` on Windows), which Rundock writes on every open and names in the settings file the runtime is launched with, so whatever it says answers every permission check; `.mcp.json`, handed to the runtime with `--mcp-config`, whose stdio servers start at the next spawn as their own processes; `.rundock/mcp-secrets.json`, which supplies the `env` and `headers` those servers start with, so an `env` such as `NODE_OPTIONS` changes what one runs; the project's `.claude/settings.json`, whose hooks and `env` the runtime acts on for every agent spawned there; and anything under `.claude/hooks/`, the scripts those hooks commonly run. Each is an answer file to the hook, as `.rundock/state.json`, `.rundock/permissions.json` and `.claude/settings.local.json` are (`LAUNCHER_FILES`, `WHAT_RUNS_FILES` and `WHAT_RUNS_DIRS` beside `WORKSPACE_ANSWER_FILES` in `scripts/permission-hook.js`). A write, edit or delete by a file tool, or a shell command that writes, edits or deletes one (a redirect, `tee`, `cp` or `mv` onto it, `sed -i`, `rm`), asks every time with Allow and Deny only, in Notes and Code mode alike; no saved "Always allow" and no folder grant answers it (`crossingCovered` in `lib/workspace/boundary.js` recomputes this from the path); and when Rundock cannot be asked it is refused rather than allowed. **The launcher is the exception, and is refused outright.** Rundock writes it on every open and puts back any other change to it without a card (below), so an Allow could never hold; a write to it, this workspace's or another Rundock workspace's, by a file tool or a shell command, is refused before any card, with a reason, in both modes, as the settings file the runtime is started with is. Reading them is free. A shell command asks only when it can write one (`answerFileWriteWords` in the hook): a redirect or `tee` into it, a copy, install or `dd` onto it, `install -d` naming it, and anything else naming it unless its program is known to only read what it names, so `sed -i` (and macOS `sed -I`), `perl -i`, `rm`, `mv`, `ln`, `touch`, `truncate`, `chmod`, `git checkout` and `git restore` ask, and so do `git add` and `git commit` naming one, while `git diff`, `git log`, `jq`, `diff` and a copy out of one do not. A program with an option that writes a file it is given with no redirect is never taken as a reader: a pager's log file (`less -o`), `sdiff -o`, `tree -o` and `file -C` ask like any program the check does not know, and `tree -o` and `file -C` are not reads in the shared read-only vocabulary either. A command that removes, moves or replaces a folder holding answer files (`rm -rf .claude`, `mv .rundock old`), copies or moves into a folder under an answer file's name (`cp backup/.mcp.json .`), or names a glob that can match one (`rm -rf .claude/*`, `rm -rf .*`, `rm -rf .[!.]*`) asks the same way, with braces expanded as the shell would first (`rm -rf .{claude,rundock}`); the workspace root itself is not such a folder, so `git add .` and `rm -rf *` are judged as before. **In code handed to an interpreter, a path that names one counts as written unless every use of it is a listed read** (`codeUse` and `CODE_READS_ALLOWED` in the hook). The path is a literal or one built from parts: a join (`os.path.join`, `path.join`, `path.resolve`, `File.join`), pathlib's `/` and `.joinpath`, a path constructor, an f-string, a template, Ruby's `#{}` or `+`, judged as the whole path, so `os.makedirs(os.path.join('.rundock', 'scratch'))` and a write to `Path('.claude') / 'agents' / 'new.md'` are ordinary while `.claude/settings.json` built the same way is not. A part worked out as the code runs is unknown: the known folder before it is judged as one the path may be inside, and the known path after it on its own. A use is a read only if it is one of these, and anything else asks, an alias, an imported runner or a helper included: a call that only reads or tests it (`print`, `pprint`, `puts`, `pp`, `len`, `repr`, `log`, `info`, `warn`, `error`, `debug`, `exists`, `isfile`, `isdir`, `islink`, `lexists`, `getsize`, `getmtime`, `stat`, `lstat`, `access`, `existsSync`, `statSync`, `lstatSync`, `accessSync`, `readFileSync`, `readFile`, `createReadStream`, `read_text`, `read_bytes`, `read`, `readlines`, `exist?`, `exists?`, `file?`, `directory?`, `require`); an `open` with no mode or a read mode written as a literal (`open`, `openSync`, `fopen`); the source of a copy (`copy`, `copy2`, `copyfile`, `copytree`, `copyFile`, `copyFileSync`, `cp`, `cpSync`, `cp_r`, `copySync`, `copy_file`, `copy_entry`); a listing it is the source of, judged by what is done with the listing (`listdir`, `scandir`, `walk`, `glob`, `iglob`, `rglob`, `iterdir`, `readdir`, `readdirSync`, `opendir`, `entries`, `children`); a loop over it, judged by every use of the loop's variable; a comparison or a membership test (`==`, `!=`, `===`, `!==`, `<=`, `>=`, `in`, `not in`, `is`, `is not`), and a set, list or tuple used only for them, a `set(...)`, `frozenset(...)`, `new Set(...)` or `new Map(...)` built from one included; a pattern handed to a string method, or an item handed to a list method, on a value that is neither a module nor a path (`replace`, `replaceAll`, `startswith`, `endswith`, `startsWith`, `endsWith`, `split`, `rsplit`, `strip`, `lstrip`, `rstrip`, `includes`, `indexOf`, `lastIndexOf`, `find`, `rfind`, `count`, `removeprefix`, `removesuffix`, `partition`, `rpartition`, `match`, `search`, `test`, `sub`, `gsub`, `contains`, `has`, `remove`, `append`, `add`, `discard`, `index`, `insert`, `extend`, `push`, `unshift`, `delete`, `get`, `pop`), and a key deleted from a mapping with `del`; a read or a test with it as the receiver (`exists`, `is_file`, `is_dir`, `is_symlink`, `is_absolute`, `stat`, `lstat`, `read_text`, `read_bytes`, `samefile`, `startswith`, `endswith`, `startsWith`, `endsWith`, `includes`, `indexOf`, `find`, `count`, `exist?`, `file?`, `directory?`, `has`, `get`); a method whose result carries it on, judged by that result's use (`resolve`, `absolute`, `expanduser`, `as_posix`, `with_suffix`, `with_name`, `relative_to`, `parent`, `name`, `stem`, `suffix`, `iterdir`, `glob`, `rglob`, `lower`, `upper`, `strip`, `lstrip`, `rstrip`, `split`, `format`, `encode`, `replace`, `toLowerCase`, `toUpperCase`, `trim`, `slice`, `substring`, `toString`, `normalize`, `to_s`); a name it is put in, judged by every use of the name, or, in code run top to bottom, by the uses before the name is next given a value at the top level (a use in a loop or a function counts wherever it is); and a statement on its own, such as a docstring. So `open('.mcp.json')`, `json.load(open('.mcp.json'))`, `readFileSync('.claude/settings.json')`, `os.path.exists('.mcp.json')`, `print('.claude')`, `dirs.remove('.claude')`, `str(p).replace('.claude/', '')` and a set of folders a walk skips do not ask, while `open('.mcp.json', 'w')`, `shutil.rmtree('.claude')`, `import os as o; o.remove('.mcp.json')`, `open(f'{d}/settings.json', 'w')`, a mode kept in a variable and a path kept in `self.path` do. A command the code runs (`os.system`, `subprocess`, `child_process`, a runner imported by name, under an alias or in a bracketed list over several lines) is read as a command, word by word, each word filled in from the names and loop values it may hold, so `for d in ('.claude',): subprocess.run(['rm', '-rf', d])` and `from subprocess import call; call('rm -rf .claude', shell=True)` ask. `git clean -x` and `-X` name no file but remove the ignored `.rundock` folder: Notes mode grades `git clean` destructive, and Code mode asks every time while `.rundock` is in its reach. Not caught, because nothing in the command names the file or a folder holding it: a git command that rewrites tracked files wholesale (`git checkout <branch>`, `git stash`), an archive unpacked over the workspace, a copy of a folder's contents into the workspace root (`cp -a template/. .`, or BSD `cp -R template/ .`), a write made inside a program's own text that is not read as code (sed's `w` command, `awk '{ print > ".mcp.json" }'`), a path that code given to an interpreter builds as it runs rather than names in a string literal, or a script. Nor is a literal with the open mode written into it, as in Perl's two-argument `open(F, ">.claude/hooks/pre.sh")`: the literal is not the file's name, so it matches nothing (the three-argument `open(F, '>', '.claude/hooks/pre.sh')` names the file and asks). Hooks declared in an agent's or a skill's frontmatter are not among these files either: they live with the agents and skills, which a file tool may not write at all (below). Paths are compared by their real names, so a case variant on a case-insensitive filesystem, a workspace opened through a symlink and a `.claude` folder kept elsewhere through one all reach the same file; another Rundock workspace's copies (a folder holding `.rundock/state.json`) ask too. The card says what the file decides: for a launcher, where a card is still drawn (a Codex agent's escalation that reaches one), that it starts the permission checks themselves; for the others, that it decides what Rundock or Claude Code runs, outside the sandbox. The hook reads the command a tool call carries, not what a script does once it runs, so a write made by a script, or by code that builds its path as it runs, never meets it: where the operating-system block runs, it refuses a sandboxed write to the launcher, `.mcp.json`, `.rundock/mcp-secrets.json`, the project settings and `~/.rundock-console` however it is made. **Rundock's console folder under home always asks too.** `~/.rundock-console` holds the script Rundock opens in Terminal when a person reconnects Claude Code, so what it says runs outside every sandbox the moment they press the button. A write there, to the folder or anything in it, by a file tool or a shell command (a glob at home that matches it included), asks every time with Allow and Deny only, in both modes, no stored grant answers it, and it is refused when Rundock cannot be asked, wherever the workspace is: with the workspace at the home folder it is otherwise ordinary work inside it (`RUNDOCK_CONSOLE_DIR` in `scripts/permission-hook.js`). A read is judged as before. The detect-and-restore guard does not watch it, so a Codex agent's write there, which never escalates inside a home-folder workspace, is not caught. Behind both, for Claude and Codex turns alike, the detect-and-restore guard (`lib/workspace/answer-file-guard.js`) watches every file the hook names, lists `.claude/hooks/` at every check (up to 64 files, four folders deep) so that a script added during a turn is a change from nothing, and puts back a change Rundock did not make during a turn, offering it on the put-back card. A folder on the way to a watched file that has been swapped for a link is taken away before anything is put back, so a restore never lands where the link points; a link a person had there from the start is kept, or pointed back if it was moved. For a Codex agent, whose writes inside the workspace never escalate, that guard is the only line. `.mcp.json`, the per-user connector file and the hook scripts are edited by hand and by git too, so a change found as a turn starts is taken as the new starting point, as the Claude Code settings files are, and named in a quiet notice in that turn's conversation, since a late write by an agent's background job would stand the same way. A hand edit to one of them made while an agent's turn runs cannot be told from the agent's, so it is put back and offered on the put-back card like one. The launcher is this copy of Rundock's own: a change to it, whether an agent made it or another copy of Rundock open on the same workspace wrote its own, is put back to the one this copy wrote, with no card and nothing said to the agent. A Claude agent's write that a person allowed on the hook's card stands: the Allow marks each answer file the card named, for that conversation, with the content the card showed (a Write's content, or an Edit or a MultiEdit worked out against the file as it stood, a MultiEdit's edits applied in turn), and the guard takes the next matching change during one of that conversation's turns as the new starting point, once, with no second card. A shell command names no content, so its mark covers the path, and only for that command: it is dropped at the check made as that command finishes (the PostToolUse check, where Rundock owns the settings file; elsewhere it lasts until the turn ends), so a later write in the same turn is put back; a mark nothing used ends with the turn, and no launcher write is ever allowed to begin with. Rundock's own writes of these files are made from its server, which neither the hook nor the sandbox judges: the launcher on every open, sound hooks muted in the project settings, and a connector an agent asks for, written into `.mcp.json` only once the person allows it (below). Rundock never writes `.rundock/mcp-secrets.json`; the person does.

  **An Allow on these cards may not take effect for the files Claude Code protects itself.** Claude Code's documentation lists `.mcp.json` and the whole `.claude` folder among its protected paths (code.claude.com/docs/en/permission-modes, "Protected paths"): in `acceptEdits`, the mode Rundock runs it in, a write to one is never approved by the runtime on its own but prompted, its own allow rules do not pre-approve it, and output redirects and `tee` are checked against the same list (code.claude.com/docs/en/permissions). Rundock runs it with nobody at its prompt, so such a write is refused, which is what was recorded when two agents tried to edit `.mcp.json` with their file tools after the person had approved. The documentation lists `cp`, `mv` and `sed` among the commands `acceptEdits` approves on its own, and says writes to protected paths are prompted in that mode all the same. It does not say whether a PreToolUse hook's allow lifts the protection; the refusals recorded for `.mcp.json` happened while Rundock's hook was already answering allow for that in-workspace write, which suggests a hook's allow does not lift it for file tools. So the card for `.mcp.json`, `.claude/settings.json` and the hook scripts says that Claude Code may refuse the change even after it is allowed, rather than promising otherwise. `.rundock/mcp-secrets.json` sits in `.rundock`, which Claude Code does not protect, so an Allow there takes effect; the launcher, also in `.rundock`, is never offered an Allow (above). This is from the documentation, not from running the runtime.

  **A file tool's write into the workspace's own agents and skills is refused outright, in every run.** Agents and skills in a workspace are changed only by Doc (`rundock-guide`), whose save markers the server writes. A Write, Edit, MultiEdit or NotebookEdit whose target is in the workspace's `.claude/agents/` or `.claude/skills/`, or is one of those folders, is refused by the hook before any card, saved answer, folder grant or mode can answer it, in Notes and Code mode, in a conversation and in a routine (`isWorkspaceTeamFolderEdit` in `scripts/permission-hook.js`). In a conversation Claude Code refuses these writes itself; a routine runs it with `--dangerously-skip-permissions`, and there a file-tool write into the agents folder went ahead and changed an agent's instructions for its next run, so the hook's refusal is the one that holds in a routine. Paths are compared as they are for the runtime home's folders: a case variant where the filesystem folds case, a relative path, `..` segments, a workspace opened through a symlink and a target whose folder does not exist yet all reach the refusal, while a neighbor such as `.claude/agents-old/` or `.claude/commands/` does not. The reason tells an agent in a conversation to hand the change to Doc or ask the person, and an agent in a routine to say in its final message what it wanted to change. Reading and listing the two folders is unaffected, and a shell command is not covered by this refusal.

  **A connector an agent asks for is written only once the person allows it.** An agent adds or removes a connector with the `SAVE_CONNECTOR` and `DELETE_CONNECTOR` markers; the window turns each into a message and the server writes `.mcp.json` (`handleSaveConnector` and `handleDeleteConnector` in `lib/protocol/handlers/team.js`). Each message first raises its own permission card through the server's own permission request, naming the server and exactly what it would run (the command and its arguments, quoted as a shell would need them) or reach (its URL), with the names of the environment variables and headers set for it and any header helper it runs. The window grades it high, so it offers Allow and Deny only and no saved allow answers it. Only an Allow a person gave on that card writes: Deny, an allow that came from no card, or no answer before the timeout, which includes no window to ask, writes nothing, and the same marker in a later reply raises a card of its own. Settings has no connector writer of its own: its Connectors tab hands adding one to the guide, which uses the same marker and meets the same card.

  **Only Doc's replies change agents and skills.** An agent asks for an agent or skill file to be saved or deleted with the `SAVE_AGENT`, `CREATE_AGENT`, `DELETE_AGENT`, `SAVE_SKILL` and `DELETE_SKILL` markers. The server acts on them once, at the end of the turn, in `applyTeamMarkers` (`lib/agents/team-markers.js`), reading the text it collected from the agent's own process and the agent id it recorded for that process when it started it: never the reply's words, a marker's attributes, the conversation's current process, or anything a window sends. Only a turn recorded as Doc's (`rundock-guide`) writes, through the handlers in `lib/protocol/handlers/team.js`, and never Doc's own file or an agent whose frontmatter declares `type: platform`. Any other agent's marker is refused, nothing is written, and the conversation's windows are told who asked, for what, and that only Doc can change the team. A Codex agent is never Doc. A routine's output, and a turn that ends without a result (an intercepted or blocked Agent call, a crash, a cancel), are not acted on. The window sends none of these changes, and the six socket messages that used to make them (`save_agent` with its legacy names `create_agent` and `update_agent`, `delete_agent`, `save_skill`, `delete_skill`) are refused. This rule covers the markers only: a direct write into those two folders with a file tool or the shell is a separate question.

  **The agent's next turn is told what Rundock did with its markers.** Each outcome `applyTeamMarkers` returns (saved, deleted, refused, failed) is kept for the conversation by `keepOutcomes` in `lib/agents/team-notes.js`, in memory and on the conversation's record (`teamOutcomes` in `.rundock/conversations.json`), so a restart between the turn and the next one loses nothing. The next message the person sends opens with a `WHAT RUNDOCK DID WITH THE LAST REPLY:` heading and one line per outcome, once, and the outcomes are then removed from memory and the record. Claude Code receives it through a wrapper on the process's stdin set when the process starts, so every place a user message is written carries it; Codex receives it in the input `withAgentNotice` builds. A resume Claude Code refuses puts the outcomes back for the turn started in its place. The note is built only from the fixed fields of each outcome (kind, name, who asked, the outcome and Rundock's own message), never from the reply's text or a marker's attributes, and the heading is in the list of Rundock's own lines, so the history never shows it. If storing, building or delivering it fails, the failure is logged and the person's message goes as sent. Each outcome is also written once to the conversation's transcript, after the reply that asked, as a line of type `team`; the history gives it back as Rundock's own line, and the page keeps it with its own conversation, so it is shown there however many windows are open, whichever conversation was on screen, and after a reload.

  **What Rundock decides for an agent is never inherited.** The permission hook reads Code mode from `RUNDOCK_CODE_MODE` alone, and `RUNDOCK_CONVO_ID` names the conversation it asks for; `getSpawnEnv` in `lib/runtime/claude.js` removes both from the environment Rundock was launched with before setting its own, so a value present at launch can neither put a Notes workspace under Code-mode grading nor give an agent a conversation it does not have. `launchctl setenv`, `unsetenv`, `config`, `load`, `bootstrap` and `submit` change what every program started from then on inherits, Rundock included the next time it is opened from the Dock, or start a program under launchd, so they always ask in both modes: in Code mode they are graded like elevation (`scripts/code-mode-verdict.js`), and in Notes mode they are part of the shared definition of an irreversible command (`isDestructiveShellCommand` in `public/read-only-shell.js`), so the card is graded high, no saved allow answers it, and the hook refuses it when Rundock cannot be asked. Notes mode grades `launchctl` high too when the line does not spell its subcommand: given none, it reads them from standard input (`echo setenv X 1 | launchctl`), and one starting with a quote, `$`, a backtick or a backslash is filled in by the shell. `print`, `list` and `getenv` run as before.

  **A permission hook that cannot answer, or cannot read what it was asked, refuses the call.** Claude Code reads a PreToolUse hook that prints nothing as having no objection, so `scripts/permission-hook.js` installs its handlers for an exception (`uncaughtException`), an unhandled rejection (`unhandledRejection`) and a process left with nothing to wait for (`beforeExit`) before it requires anything, and each refuses the call in the words any request the hook could not check gets, a routine's telling it what to do next. A rejection is refused under every `--unhandled-rejections` mode `NODE_OPTIONS` can name (`throw`, `strict`, `warn`, `warn-with-error-code`, `none`), because that variable is inherited from wherever Rundock was started, and under the last three a rejection used to leave the hook to carry on and allow the call. Input the hook cannot read (not JSON, empty, cut off, or JSON that is not an object) used to pass through, which the runtime took as no objection; it is now refused the same way, before anything is asked of the server, so it raises no card. A request the hook cannot name, or whose input it cannot read, is refused inside Rundock the same way, before anything is asked of the server: one whose `tool_name` is missing, is not a string, or is empty or only spaces, and a file, shell or connector tool whose `tool_input` is missing or is not an object. Every check keys on the tool name, and those tools' checks read the input too, so such a request matched none of them and, with the server unreachable, was allowed as ordinary access. A tool named properly whose checks read no input, and a tool the hook does not know, are judged as before, and a finished tool is answered as before, proved by running the real hook in `test/unit/hook-unnamed-request.test.js`. The hook prints one answer for each call, and an answer counts only once the whole of it has been written. It is written straight to standard output's descriptor: a write through `process.stdout` returned before the text had gone anywhere and reported a failure, a reader that had gone for one, only after the hook had exited 0 with no answer, which the runtime read as no objection. A reader that has stopped reading is waited on for two seconds at most. An answer that cannot be written is never followed by another: the hook writes its reason to standard error and exits with code 2, which the runtime reads as a block on PreToolUse, a refusal in its own words and an allow, a card approved in Rundock included, in the words of any request the hook could not check. A rejection or an error arriving after an answer adds nothing and changes nothing. An allow is written one turn after it is decided, by `setImmediate`: Node hands an unhandled rejection to its handler only once the turn that made it is over, and an allow written, and exited on, inside that turn let the call through with a rejection from the same turn, one made as a card's approval arrived for instance, never handled. By the time the allow is written, that rejection has refused the call, and the allow prints nothing. A refusal, and an answer that decides nothing, are written in the turn they are decided. That Claude Code blocks the call on that exit is measured: `scripts/hook-block-truth/capture.js`, run by hand against the installed Claude Code with a stand-in for the messages API, so no account is used and no model is called, and in a folder made new for the run, private to the user and outside the repository, so no link left inside the repository can lead what it creates or removes elsewhere, recorded the permission hook, a card approved and the reader of its standard output gone, exiting 2, and the Bash call it guarded never running, with the hook's reason as the tool result the model was sent. `test/unit/hook-block-capture.test.js` holds that record, in CI, and runs today's hook the way the capture ran it. Outside Rundock, and after a tool has finished, none of this decides anything, and an answer that cannot be written still ends in exit code 0. Not covered by the hook itself: a hook killed from outside, or stalled past the runtime's 300-second limit, which is answered by how the hook is registered (the next paragraph). Proved by running the real hook as its own process in `test/unit/hook-never-crashes.test.js`, with every failure forced from outside the hook, by a `--require` preload or by the pipe the test gives it as standard output, never by a switch in the hook.

  **A permission hook that fails blocks the call on Claude Code 2.1.295 and later.** Every PreToolUse entry Rundock writes into the workspace's `.claude/settings.local.json` carries `"onFailure": "block"`, from one constant, `HOOK_ON_FAILURE` in `lib/workspace/scaffold.js`. Observed against real Claude Code, with a stand-in for the messages API and stand-in hook scripts registered in the shell form Rundock writes: on 2.1.295 and 2.1.318, a hook that exited 1, was killed with SIGKILL, passed its timeout, printed JSON that did not parse, or could not start blocked the Bash call it guarded when the field was set, and the model was told the hook had failed and that the call was blocked because `onFailure` is `"block"`; without the field, every one of those let the call go ahead, and the model saw an ordinary successful result. On 2.1.294 and 2.1.250 the field was accepted and ignored: the rest of the settings file applied as before, every one of those failures let the call go ahead with the field or without it, and a deny the hook printed still blocked the call. So on 2.1.295 and later a hook that fails blocks the call, and before 2.1.295 the call goes ahead and the hook's own refusal is the only answer. The field carries a hazard of its own: on 2.1.295 and 2.1.318 a value other than `"block"` or `"continue"` made Claude Code skip the whole settings file, the permission hook, the permissions and the sandbox block with it, without a word in print mode. That is why only the constant is ever written. The reconcile on open sets it on a Rundock entry where it is missing or holds anything else, leaves an entry Rundock did not write as it is, and leaves a settings file it cannot read or parse exactly as it is, logging why, rather than rebuilding it. It writes the file whole: to a temporary file beside it, renamed over it only once that write has finished, so a write that fails partway, on a full disk say, leaves the file as it was. Going back to an earlier release keeps the field: the v0.15.7 release's own scaffold, run on a workspace this release wrote, left the settings file byte for byte, so a hook that fails still blocks the call on 2.1.295 and later, as `scripts/hook-on-failure-undo/captured-earlier-release.json` records. The PostToolUse and PostToolUseFailure entries do not carry the field: they run after the tool has, so there is nothing left to refuse. Held by `test/unit/hook-on-failure.test.js`. Versions between those named were not run, nor interactive mode.

  **A PowerShell command runs with no card only when every part of it is a read Rundock can name.** On Windows no sandbox sits under the card, so this is the only check between an agent's PowerShell command and a write, a send or a delete. `isReadOnlyPowerShellCommand` in `public/read-only-shell.js` is the one reading of PowerShell: the card grader (`classifyRisk` in `public/permissions.js`) grades a PowerShell command low only when it reads it as a read, and the permission hook frees a crossing into the runtime's own home on the same answer. A command is a read when every part of it, split at `;`, `|`, `&&`, `||` and each new line, starts with one of these, in any case: `Get-ChildItem`, `gci`, `dir`, `ls`, `Get-Content`, `gc`, `cat`, `type`, `Get-Item`, `gi`, `Get-Location`, `gl`, `pwd`, `Test-Path`, `Resolve-Path`, `Split-Path`, `Select-String`, `sls`, `Measure-Object`, `Select-Object`, `Sort-Object`, `Format-Table`, `Format-List`, `Out-String`, `Write-Output`, `Write-Host`, `echo`, `Get-Date` and `Where-Object`. The list is named one cmdlet at a time and not matched by verb, because a `Get-` name is a convention nothing enforces: `Get-Clipboard` and `Get-Credential` hand an agent what it should not see unasked, and a cmdlet written tomorrow can take any name. Anything the reading cannot follow all the way is not a read, and cards: a command inside another (`( )`, `$( )` inside double quotes too, `@( )`, a script block, `&`, dot-sourcing), a backtick, a here-string, the `--%` token, a comment, a redirection to anything but `$null` or another stream, a character outside plain ASCII other than a letter, mark or digit, a variable or a bracket where a command name should be, and text it cannot read at all (an unbalanced quote or bracket, a lone backtick, a control character, more than 8,192 characters). `Invoke-Expression`, `powershell`, `pwsh`, `cmd` and `Start-Process` are not on the list, so a command that starts another shell cards too. A failure inside the reading is read as not a read, so the command cards and nothing is allowed on its behalf. Bash keeps its own reading, `isReadOnlyShellCommand`, unchanged. The grader and the reading are pinned in `test/unit/permissions.test.js`, the hook in `test/unit/powershell-reads-hook.test.js`, the card in `test/unit/powershell-read-cards.test.js`, and the whole path, from the hook through the server to the card and back, in `test/integration/powershell-read-approvals.test.js`.

  **`sort` and `date` run with no card only in the forms that read.** Notes-mode routines list their folder with a pipe into `sort` and check the date, and a routine has nobody to answer a card. `isReadOnlyShellCommand` in `public/read-only-shell.js` reads each of them option by option, as it reads `find`: a `sort` or `date` is a read only when every option on the line is on its list of reading options, and any other option asks, one the list has never heard of included. The options are read as getopt reads them, a short bundle letter by letter (`-rno out` is `-r -n -o out`), after the shell has taken quotes and backslashes away (`'-o'` is `-o`), and a line whose words the shell fills in (a `$`, a glob, a brace, a redirection) or that cannot be read cleanly is not a read. `sort` reads with its ordering, key, field separator, buffer size, check, merge and unique options. `sort -o`, `--output`, `-T`, `--temporary-directory` and `--compress-program` ask, because they write a file, put files where they are told or run a program. `date` reads alone, with a `+` format, and with `-u`, `-R`, `-I`, `-r`, `-z`, `-v`, `-d` and `-j` and their GNU long forms. `date -s`, `--set`, a time operand (one not starting with `+`) and `-f` without `-j` ask, because they set the system clock. The lists are checked against both the macOS and the GNU manuals, because the same text runs under either. The permission hook reads the same definition, so a reading `sort` or `date` of a file under the runtime's own home is freed exactly as `cat` and `stat` of it are, a writing form keeps its crossing as a write, and the credential file still cards on any access. The reading is pinned in `test/unit/permissions.test.js`, the hook in `test/unit/sort-date-reads-hook.test.js`, and the card in `test/unit/sort-date-read-cards.test.js`.

  **An option is judged as the shell hands it to the program, so quoting or escaping an option that writes or runs never makes it a read.** `isReadOnlyShellCommand` in `public/read-only-shell.js` judges the options of `find`, `rg`, `tree`, `file`, `sort` and `date` on the words the shell hands the program, after it has taken quotes and backslashes away: `'-fprintf'`, `"--pre"`, `\-o` and `-fpr'int'f` are judged as the `-fprintf`, `--pre` and `-o` they are, and ask as those do. A long option cut short the way getopt_long accepts is judged as the option it names (`file --comp` is `--compile`). A segment of one of these commands whose words the shell fills in (a `$`, a backtick, `$'…'`, a wildcard at the start of a word, a brace) or that cannot be read cleanly (a quote left open, a backslash with nothing after it, a control character, more than 8,192 characters) is not a read, so it asks. A wildcard after a plain first character other than `-` still reads for `find`, `rg`, `tree` and `file`, as in `rg 'TODO' notes/*.md`: every name it expands to starts with that character, so none of them is an option. That wildcard and a `!` that is a word of its own, which bash and zsh hand over as the text `!` (`find . ! -name x`), are the only two exceptions to the rule that a character outside the plain set makes the segment not a read. Commands split where the shell splits them: a backslash outside single quotes takes the next character with it, so `\"` and `\'` open no quote, and each line after one is judged as the command it is. No quote character that opens nothing in bash hides a command either: a quote in a comment, one escaped inside `$'…'`, one in a here-document's body, and the quotes inside a substitution held in double quotes are each read as the text they are (`shellView`), and every reading reads the line that way as well as as written. A line whose quotes bash 3.2, a later bash and zsh read differently, or that this reading cannot follow to its end, is not a read, and neither is one with a `(` or `)` outside its quotes, where zsh's glob qualifiers, its `=( )` and a `case` pattern run a command behind a word that reads. In Code mode the verdict reads the line both ways as well, and a line the shells read differently, or one holding a command inside a word that only zsh runs, always asks. In Notes mode a line with a `(` inside a word, outside its quotes, is graded high risk by `classifyBashRisk` in `public/permissions.js`, however the word starts and wherever it sits (`ls 'a'*(e:'cmd':)`, `cat =(cmd)`, `echo $(ls *(e:'cmd':))`), because zsh runs the code written inside that file pattern as it expands the word, and so is a line whose view fails or nests deeper than the view follows. Such a line is carded every time and never offers "Always allow", so no saved answer covers it: a saved answer is keyed on the leading command alone, so "Always allow ls" would otherwise cover the code inside the pattern. A function definition (`f() { echo hi; }; f`) puts a `(` inside a word too, and is graded high with them; Code mode already asks about it. The card says why it asks, in the context sentence `describeToolRequest` gives: "This line has a parenthesis inside a word, which the shell can use to run hidden code, so Rundock asks every time and there is no Always allow.", or, for a line whose view failed or stopped short, "Rundock could not read this line all the way through, so it asks every time and there is no Always allow." A line graded high as destructive first keeps the sentence its leading command gives. Only a space, a tab and a newline separate words, as in bash, so any other blank in a segment whose options are judged (a form feed, a vertical tab, a no-break space or another Unicode space), or a carriage return on its line, makes the line not a read. **Nothing the earlier reading asked about reads now.** Every line is also split as it is written, and `find`, `rg`, `tree` and `file` are also judged on their words as written, the way every line was judged before, and a line reads only when both readings read it. Option-like text inside a quoted operand (`rg "x --pre" .`), an option split across quotes where the earlier reading asked (`find . -na'me' x`), and an escaped quote in front of a separator (`grep "a\"; rm x" f`) ask as they always have. `test/unit/read-only-on-main.test.js` holds this to the earlier verdicts, recorded by `test/tools/record-read-only-on-main.js` from the merge base over every command the read-only tests judge, and checked against the graders at that base wherever history holds it. The permission hook reads the same definition, so a quoted writing option keeps its crossing as a write in Notes mode and in Code mode, a quoted write of an answer file is still an answer-file write, and the hook reads the paths in a bash command as it always did and in the line's view as well, where an escaped quote and every other quote character that opens nothing is a space, so none of them hides a path from its crossing check and no path it saw before is lost. The reading is pinned in `test/unit/permissions.test.js`, the hook in `test/unit/quoted-options-hook.test.js`, and the hook with the reading failing in `test/unit/hook-never-crashes.test.js`; the view in `test/unit/shell-view.test.js`, and through the hook in both modes in `test/unit/shell-view-hook.test.js`; the high grade and the card's sentence through the card code in `test/unit/zsh-pattern-cards.test.js`, through the real hook, server and window in `test/integration/zsh-pattern-saved-answer.test.js`, and against real zsh in `test/unit/shell-view-shells.test.js`. The lines whose grade this rule moves, between any two commits, are listed and checked by `test/tools/zsh-pattern-grade-moves.js`.

  **The agent's own folder (`~/.claude`) is graded by persistence, not by location.** A model tool reading anywhere under it raises no card, with one exception. `.credentials.json` is the **secrets registry**: it cards on any access, read or write, in both modes, and no grant, mode or setting silences it, because a credential leak cannot be undone. **Where the operating-system block runs, a write to it is refused by the operating system as well:** the writable-roots list in the OS-guarantee row names `~/.claude` as a whole (the runtime's own bookkeeping lives there), and the block's `denyWrite` list names every path this registry calls a secret, in both runtime homes. On macOS the runtime keeps its live credential in the Keychain and falls back to the plaintext `.credentials.json` only when the Keychain is unavailable, so the deny covers that plaintext fallback and Codex's `auth.json`, not the Keychain item. The deny covers writes only. Reads, which are all that stealing a token takes, are guarded by the permission card alone. The deny list is built from this registry rather than restated, and a test fails if the two differ. Where no block runs (Windows, Linux, or the switch off), the permission card holds the line for writes as well. Writing to `agents/` or `skills/` is **refused outright, not carded**: a pre-existing guard denies the write before it reaches the card, and correctly so, because Rundock reads the *workspace's* agents and skills, never the global ones, so an edit here would land somewhere the app never looks, report success, and change nothing. Writing to any other **persistence surface** (`plugins/`, `commands/`, `hooks/`, `settings.json`, or the global instruction files `CLAUDE.md`, `rules/` and `output-styles/`) **splits by which tool is writing, and the split is the runtime's, not this product's.** A model **file-edit tool** (`Write`, `Edit`, `MultiEdit`, `NotebookEdit`) is **refused outright**: measured against the runtime, it rejects a file-edit write anywhere under `~/.claude` as a sensitive file whatever is approved here, so a card offering to allow one is a promise this product cannot keep, and approving it only to be refused underneath teaches the reader that the card means nothing. Nothing is lost by refusing first, because that write could not land either way, and what the reader wants to change almost always lives in the workspace's own `.claude`, which is the copy Rundock reads. A **shell command** reaching the same path is **not covered by that refusal and still cards**, and is approvable. Approving it lets the command run. Where the operating-system block runs, the block's `denyWrite` list names `settings.json` and the `plugins/`, `hooks/` and `commands/` folders, with `skills/` and `agents/` above, so the sandboxed write is refused whatever the card said, as the runtime's own deny list also refuses it in the releases that carry one. A write to the global instruction files (`CLAUDE.md`, `rules/`, `output-styles/`) is not in the block's deny list and lands once approved, unless the installed runtime's own list refuses it, as the 2.1.259 bundle's does (a static read of the bundle, not a live measurement). Where no block runs, and for a retry outside the sandbox, which cards again, a write to any of them lands. What is stated is what this product does, which is to card the command rather than refuse it, and a test reads the hook's verdict for both families at one persistence-surface path so this paragraph cannot drift from what the hook does. Writing anywhere else in the folder (`projects/`, `cache/`, `paste-cache/`, `downloads/`, `tasks/`, `file-history/`, `shell-snapshots/`, `session-env/`, `history.jsonl`) is free: it is scratch and transcripts, the agent's own furniture, reached freely by the same agent in a terminal. There is no narrow remembered grant: an earlier design carded the whole folder and then carved a hole back out of it with a folder-scoped grant labelled for one use and stored for a wider one, which is exactly the mismatch a boundary drawn by persistence rather than by location no longer needs.

  **The other runtime's home (`~/.codex`) is graded on the same three tiers, by the same registry shape.** Rundock spawns Codex as well as Claude, and for a long time only one of the two homes was graded: an agent reading its own configuration was silent on Claude and raised a card on Codex, which Rundock's own Connectors tab reads and displays without asking anyone. `auth.json` is the **secrets registry** for this home, the counterpart of `.credentials.json`: it cards on any access, read or write, in both modes, and no grant, mode or named working folder silences it. That tier is not only about noise. Untiered, `~/.codex` was ordinary outside access, so its card offered a standing grant on the whole folder, and anyone who accepted it to stop being asked about configuration would have silenced every later read of the credentials sitting beside it; the secrets tier refuses a folder grant outright, which is why credentials belong in it and why naming `~/.codex` as a working folder does not exempt them either. `config.toml` is this home's `settings.json`: **free to read, cards on write**, together with `prompts/` and the global instruction files `AGENTS.md` and `rules/`. **The global instruction files of both homes are protected in both modes**, because a write to one plants instructions every later session loads, in every workspace, including routines that run unattended; a shell write to one asks every time and is never remembered, and reading them stays free. The same fail-loud test binds these to this paragraph in both directions.

  **The Keychain holds the runtime's live sign-in token on macOS, and only the card guards it, so a command that reads or changes a Keychain item asks every time, in both modes.** The operating-system row cannot help here: the sandbox profile allows the Keychain service, because the runtime itself signs in through it, so a sandboxed command can run `/usr/bin/security`, search the Keychain and read an item. Measured rather than assumed: a lookup of a made-up item name from inside the sandbox came back "The specified item could not be found in the keychain", a search that ran rather than one that was blocked. The check runs only on macOS; on another host `security` is some other program and is graded as before. `judgeSecurity` in `scripts/code-mode-verdict.js` decides it, inverted the way the `find` rule is: every `security` subcommand asks except `help`, `error`, `show-keychain-info`, `verify-cert`, `find-identity`, and `list-keychains`, `default-keychain` and `login-keychain` without `-s` (with it they set the search list or the default), matched by exact name so a shortened or misspelled subcommand asks too. A password lookup without `-w` or `-g` asks: it prints an item's account and service rather than the secret, and those are what the next command needs to find a token. `-i` and `-p`, which read further commands from stdin, ask. The line is read by the Code-mode verdict's own reader, so the command is found wherever it sits: in a chain, a pipe, a subshell or group, a substitution, after `sudo` or `doas` (read past their options), `nice`, `time`, `env VAR=…`, `command`, `exec` or `xargs`, through `find -exec`, inside `bash -c` or `sh -c`, in a here-document or here-string a shell reads, and on a line whose here-document never ends. That line asks as one Rundock cannot read, and is still checked for the Keychain as a conservative reading: its command lines, with the unfinished body taken as data to the end of the text unless a shell reads it. What `sudo` or `doas` runs and an unfinished here-document are read for the Keychain alone, with no disk or git facts, since the line asks either way; elevations are read through eight deep, so a Keychain command under more of them asks as elevation in Code mode and is carded as before in Notes mode. The rules apply on macOS alone, and the hook judges for the host it runs on, except under one test-only seam (`RUNDOCK_TEST_PLATFORM`, read only when `RUNDOCK_TEST_SEAMS` is 1) that lets the end-to-end suite prove the Mac's rules on any host. The seam moves that check alone, never path handling or the checks on deletes; the hook ignores it when it runs as the app's Electron binary, as it always does in the app; and `getSpawnEnv` removes both names from the environment Rundock starts agents with, so a value set in Rundock's own launch environment never reaches a hook. Among reasons to always ask, the Keychain is the one the card names, and the first other reason on the line is kept beside it: a line that also deletes work git has never saved says so on the card, and the refusal adds that part of it cannot be undone. Notes mode has no verdict of its own, so the hook asks `keychainVerdict` that one question, reading disk and git facts only for a line that reaches the Keychain, and sends the answer as the request's verdict; every other Notes-mode request is graded as before.   **A workspace can name additional folders its agents work in, and naming one never reaches the tiers above.** The folders are set in Settings under Workspace, stored with the workspace, and passed to each agent as it is spawned; a named folder is compared by the same containment rule the workspace root already uses, so everything beneath it is covered, including directories created later. Naming a folder is a statement about where a team works, not a grant: it is not remembered per card, not per agent, and it says nothing about any folder that was not named. **It stops at the runtime's own home, and at a credential file reached through a link, wherever the link leads.** A named folder that contains `~/.claude`, the home directory being the obvious one, does not make anything under `~/.claude` inside: the secrets registry still cards on every access, a persistence-surface write is still refused or carded exactly as above, and both outright refusals still apply. Only the workspace a person deliberately opened is exempt from those refusals, and a named folder is not that act, because its whole value is covering folders nobody enumerated. `namedFolderCovers` in `scripts/permission-hook.js` is the single place that rule lives, and a mutation row fails if it is removed.

- **"Rundock itself contacts only GitHub, and sends none of the user's data there."** The desktop app's update check goes to GitHub releases through `electron-updater`, on launch (`setupAutoUpdate`) and from the Check for Updates menu item, both in `electron/main.js`. Packages are fetched from `https://github.com/<owner>/<repo>` with `git fetch` and `git ls-remote` (`lib/packages/extension-source.js`) when one is added, checked for updates or updated. - **"Agents cannot impersonate teammates."** The off-roster delegation block lives in the delegation interception path (`server.js`, search for the blocked-handoff notice); the orchestrator-runtime enforcement is in agent discovery.

## What Rundock does NOT do

- **No backend service.** Rundock runs entirely on your machine. There is nothing to deploy and no account to create.
- **No database as a source of truth.** Persistence is JSON files in `.rundock/` and Claude Code's own JSONL transcripts. The one SQLite file (`search-index.db`, behind universal search) is a derived, disposable index rebuilt from those sources: nothing to migrate, nothing to back up, nothing lost if it is deleted. It uses Node's built-in `node:sqlite`, so it adds no dependency.
- **No telemetry.** Rundock does not phone home, does not log usage to a remote service, does not collect crash reports. The three-dependency footprint makes this easy to verify.
- **No outbound network calls from Rundock itself beyond GitHub.** The desktop app checks GitHub for its own updates, and packages are fetched from GitHub when added, checked for updates or updated; none of the user's files, agents or conversations go with either. Every other external connection belongs to a runtime: Claude Code to Anthropic's API, Codex to OpenAI's, and any connector to its own service. Rundock does not make HTTP requests to Anthropic or OpenAI, does not handle API keys, and does not see your Claude credentials.
- **No agent-format reinvention.** Agent files use Claude Code's standard format with optional Rundock extension fields. An agent file written for Rundock works in plain Claude Code; an agent file written for Claude Code works in Rundock with reduced UI affordances. See AGENTS.md.
