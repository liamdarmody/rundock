# Extension confinement: what is enforced, and how it is proved

An extension runs someone else's code inside Rundock. This records what stops that code leaving its view, choosing which of the person's files it is handed, or acting without the person, and how each of those is proved. The consent screen's sentences about extensions are bound to the checks named here (`test/unit/extension-install.test.js`, "each trust card claim is observed by a real-engine run").

## Why the proof runs in real engines

The unit suite runs under jsdom, which enforces neither sandbox flags nor Content-Security-Policy. A unit test can show that the host writes the right attributes and applies the right rules; it cannot show that a browser honours them. So every claim below is observed in Chromium (`test/e2e/extension-confinement.spec.js`, part of the e2e step) and in the shipped Electron (`test/electron/confinement.cjs`, a release gate step), with a deliberately misbehaving extension and a local listener standing in for anywhere it might try to send data. "Nothing arrived" is read from the listener's own log.

The misbehaving extensions are in `test/fixtures/hostile/`. They name no host (the harness fills in a listener it opens on `127.0.0.1`), they are shown only canary text from a temporary folder, and they are never installed: `test/unit/confinement-fixtures.test.js` fails if any of that stops being true.

Each real-engine run includes a control: the same extension with the layer under test removed, which does get data to the listener. A pass therefore means the layer held, not that the extension or the instrument failed to try.

## What a view cannot do

| A view cannot | Enforced by | Observed by |
|---|---|---|
| Load a page, fetch, or make any request | The frame's own policy, `default-src 'none'` | Both engines |
| Replace itself with another page, taking a file with it | The app page's `frame-src 'self'` (`lib/http-router.js`); in the desktop app, a navigation guard on frames with an opaque origin (`electron/extension-frame-guards.js`) | Both engines, each layer separately |
| Keep being fed after it has left | The host answers `ready` once per frame and ends the view on a second `load` or `ready` (`public/extension-host.js`, `public/region-service.js`) | Both engines |
| Open a peer-to-peer connection | In the desktop app, WebRTC is switched off for the window. In a browser it cannot be switched off, and the consent screen says so | Desktop: nothing sent. Browser: the run observes that it is not blocked, which is why the card says what it says |
| Open another file, or a web address, without a click inside it | A click the browser recorded, focus on the view, no click or key on Rundock's own page recent enough to be that click (`public/host-gestures.js`), and a click the view did not inherit: a view mounted while a click was live cannot use it until the browser reports it lapsed (`public/extension-host.js`). A request the host cannot attribute to a fresh click in the view is put to the person in Rundock's own bar above the view, which the view cannot draw, reach or press; one with no click at all is refused and the person is told what was stopped | Chromium and the shipped Electron (real input through CDP): a view opened by another view's click takes focus by script and asks to open a file, open a web address and draft, twice, and nothing happens but the bar, with a control in which the spend and inherit rule is removed and the chain succeeds (`chain-hop.js`); in both engines with real input, a press on Open before the bar is armed lands on the disabled button, opens nothing and leaves the request waiting, and a press after it performs the request; a view that boots in the window of a tree click and moves focus into itself; in the real app, a view that asks to open a file with nobody touching it is stopped and the line says so |
| Be handed a hidden file, or write one | The renderer registry never claims a path with a segment beginning `.`, however it was opened (`public/renderer-registry.js`), and a save an extension causes is refused for a hidden path on the server (`lib/workspace/extension-file.js`) | Unit; and in the real app, extensions claiming `*.md` and `*.json` with `writes` are never mounted on or handed an agent file or `.mcp.json`, while an ordinary note of the same type is, and a save to each leaves its bytes unchanged (`test/e2e/confinement-workflows.spec.js`) |
| Be handed, or write through, a linked or hard-linked file | The server states with every read whether an extension may be handed the file: no link on the way to it or at it, observed without following one, and exactly one name, so a hard link to a hidden file is refused too (`lib/workspace/extension-file.js`). The page forwards that answer and treats no answer as a refusal, for a single-file view, an embedded one and region drawing alike; an extension's save is checked again at write time and opens the file without following a link | Unit on the rule, each server path and each page consumer; in the real app, a linked and a hard-linked file opened from the tree are not mounted and no canary reaches any frame, with a control in which the rule is removed and the canary does reach it (`test/e2e/extension-host-wiring.spec.js`) |
| Be handed any file its note does not name, or learn one exists | A view is handed a note's sources only when its manifest declares `sources` with a marker, it claimed the note by that marker, and the note lists them. The server resolves the list from the note on disk under the one extension file rule, refuses by rule every name that is hidden, linked, hard-linked, outside, a pattern, a folder, missing, duplicated or the note itself (by device and inode), and hands each as its written name and text only. No message reads, lists or searches (`lib/workspace/named-sources.js`, `public/extension-host.js`) | Unit on every rule; Chromium and the shipped Electron with a hostile view reading its own record against canaries in hidden, unnamed, hard-linked, linked and outside files; in the real app, a changed source, a removed name and a new unnamed file (see [named-sources-and-ask-evidence.md](named-sources-and-ask-evidence.md)) |
| Write a file its note does not name, or widen what it is handed | A source write names a source the view was handed and is resolved again by the server at write time, through the editors' guarded save, never through a link. No write an extension causes may change the `sources` list of the file it writes, in the host and again on the server | Both engines: every hostile write refused and no other file changed a byte, with a control in which the host's list check is removed and the server alone refuses them; a control in which the list rule is removed and the widened note reaches the write; in the real app, a source edited on disk raises the reload-theirs or keep-mine choice |
| Reach an agent, or learn anything about one | An `ask` drafts a message into a new conversation with an agent the manifest declared and the team has, and sends nothing. It needs a click inside the view, one request per click across every view (an ask on a fresh click spends it, honoured or not); the draft is cleaned of control, bidirectional and zero-width characters; nothing is posted back on success; an agent not on the team is refused before a conversation exists | Both engines, with real input in Electron (CDP), each rule with its control; in the real app, a new conversation with the agent, the message in the box unsent, no `chat` on the socket, the drafted-by line, what the agent receives when the person sends, and no saved conversation when they do not |
| Use one click for more than one request, in one view or across views | Once any view's `open`, `openExternal` or `ask` is honoured on a click, that click is spent for every view until the browser reports it has lapsed, read from the browser's own activation rather than a clock; a view mounted while a click was live inherits it and cannot treat it as its own (`public/extension-host.js`). What follows is put to the person, one request at a time | Unit, Chromium and the shipped Electron (real input through CDP): a burst of opens and web addresses on one click honours exactly one and puts the next to the person, with a control in which the click cannot be spent and the whole burst gets through; the chain across views above, with its control; each guard alone, in both engines: with only the spent-activation guard removed one view's burst of twelve requests is honoured whole, and with only the inherited-activation guard removed a frame rebuilt during a live click that nothing spent (the theme-change rebuild, `rebuild-ride.js`) opens a file on a click it never received, while with both guards, or with only the other one removed, each attack fails; in the real app, a note opened from one view's button, then its own view's button clicked within five seconds, shows the bar and Open opens the note, and Dismiss tells the view and opens nothing (`test/e2e/first-click.spec.js`) |

## Rundock UI in every frame

Every frame the host builds carries Rundock UI, the component library, inlined as the host's own code (see [rundock-ui-evidence.md](rundock-ui-evidence.md)). Every run above is therefore a run against a frame carrying it, and each proves it: before a fixture's first statement the frame builds one of every component and reports that the library is present, every factory built, and the injected stylesheet styled them, and the run fails if it did not. On top of that, a view that works every component, before and after `init`, sends nothing but `ready`; a view that uses the library and then leaves with the file reaches nothing and is ended; an embedded view carries the library and is told it is embedded; and a failure inside the library, whether a view misusing a component or a library that fails as it installs (served broken by the harness as a control), ends in the plain view with the reason named. All of it runs in Chromium and in the shipped Electron.

When the desktop app stops a view leaving, it tells the page, which ends the view and names the reason, so a misbehaving extension is stopped visibly rather than left running.

## What was deliberately left alone

The guards are keyed to frames that run extension code and to nothing else, and each thing they must leave working is checked where it runs:

- **The app page's own requests, and the request filter itself.** In the shipped Electron, with the real `webRequest.onBeforeRequest` filter, a request from the app page reaches its host and a request from a frame with an opaque origin is cancelled; without the filter the frame's request arrives, and with the real filter widened to the whole session the app page's request no longer arrives, so the check fails if the filter is ever widened. A same-origin frame, the shape of the HTML preview and the PDF viewer, still navigates.
- **Links.** In the real app with its frame policy, a web link in a conversation and a web link in a note each open outside the app, reaching their host with the app page left where it was, and a web link in an HTML preview opens outside the pane. The conversation link used to navigate the whole app page away in browser mode; rendered web links now carry `target="_blank"` and `rel="noopener noreferrer"`, which the desktop app's window-open handler sends to the system browser.
- **An agent's web fetch and the update check.** In the shipped Electron with the main window's guards installed, a real Rundock agent turn: the real server, booted in the same process with a temporary home and workspace (so the spawn helper's pid file lands there), handles the chat and spawns the runtime through its own spawn code; the runtime is a stub CLI on PATH standing in for the model, which runs its WebFetch in its own process as the real CLI does, and the request reaches a local receiver. The real updater, pointed at a local stand-in, reaches it through its own network session.
- **External links everywhere.** Every web link opens outside the app and the app page never navigates: see [external-links-evidence.md](external-links-evidence.md).

The outputs are in [trust-boundary/](trust-boundary/).

## One cost, stated

The host cannot see a click inside a frame, only that the browser's record of a click is live, and that record lasts a few seconds after the last click. So within those seconds it cannot tell a person's new click from the one already used or inherited. A person who clicks inside a view within a few seconds of the click that opened it, or of a click already honoured, is asked in Rundock's bar rather than having the click act at once; Open then does what the view asked. Nothing is refused silently, and no click is ever reused.

## Mutation coverage

Each guard above has a row in `test/tools/mutate-extension-host-guards.js` that removes it, or widens it where widening is the failure that would degrade the app, and requires a test to fail.
